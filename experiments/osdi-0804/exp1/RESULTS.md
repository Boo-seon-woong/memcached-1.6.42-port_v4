## 2. 읽으면 이렇다

**① 쓰기 비중이 부호를 뒤집는다.**

```text
C (쓰기 0%)    port −10~12%      원격화 대가가 정직하게 보인다
B (쓰기 5%)    port +30%         깊이 64 부터 역전
A (쓰기 50%)   port +505%        6 배
```

**② stock 의 쓰기 천장은 1.17 M 이고 깊이와 무관하다.** pipe 32 부터 평평하다
(1.148 → 1.198 → 1.168). 큐를 아무리 깊게 줘도 안 오른다 — **CPU 도 네트워크도
아닌 `item_lock` 직렬화**다. port 는 pac 경로가 그 직렬화를 우회한다.

**③ 지연도 같은 방향이다.** A 의 pipe=256 에서 stock 26.23 ms 대 port 4.19 ms.
처리량이 6 배인데 지연이 6 배 낮다 — 같은 병목의 양면이다.

**④ skew 는 두 쪽 다 때리지만 순서를 안 바꾼다.**

```text
              uniform → zipf θ=0.99
stock C      15.372 → 13.125   −14.6%
port  C      13.827 → 12.775    −7.6%
stock A       1.198 →  1.100    −8.2%
port  A       7.247 →  1.734   **−76.1%**
```

port 의 A 가 skew 에서 크게 무너져 격차가 6 배 → 1.6 배로 좁는다. 서버측
창에서 그 순간 **busyCPU 가 11.9**(30 코어 중)였다 — 일이 없어서 노는 것이고
`badcrc` 가 3 → 128,570 으로 뛴다. 핫키 `item_lock` 경합이다.

## 4. co-located 예비 측정과의 교차 확인

`stock-colocated/` 는 부하 생성기를 게스트 안에 둔 것이라 −31.7% 를 물 것으로
봤다. 실제로는 **워크로드마다 달랐고, 그 차이가 §2-② 를 뒷받침한다.**

```text
              co-located    off-box     차이
stock C-P256    11.220      15.372     +37.0%   ← CPU 를 나눠 쓴 대가가 그대로
stock A-uni      1.188       1.198      +0.8%   ← 대가가 없다
```

**A 는 co-location 대가를 안 문다.** CPU 가 병목이 아니라 락이 병목이니
CPU 를 나눠 써도 손해가 없는 것이다. 예비 측정이 그때 남긴 "A 는 메모리
배치가 아니라 락 경합을 재게 된다"는 각주가 이 두 줄로 확인됐다.
