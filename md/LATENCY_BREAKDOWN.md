# 지연 분해 — 클라이언트가 기다리는 것의 전부

작성 2026-08-04. 빌드 `aa55efd5979c6fd00d9c9c16`, 운영점
`mcT=30 taskset 0-29 W=24 nqp=4 reap=8 chain=8 hp=22 admit=64 batch=20 setq=1`.

**계약이 재는 `span v3` 는 클라이언트 체감 지연의 1% 미만이다.** 이 문서는
나머지 99% 가 어디에 있는지를 계측으로 밝힌 기록이다.

---

## 0. 한눈에

운영점(`pipeline=256`, GET-only) 기준:

```text
클라이언트 체감 2,277.58 µs
├ 네트워크 + 클라이언트 큐잉        ~1,786 µs   78.4%
└ 서버 체류 srv                       491 µs   21.6%
   ├ que   소켓 read → 명령 시작       108 µs    4.7%
   ├ pre   명령 → backend 진입           ~1 µs    0.0%
   ├ span v3  [계약이 재는 전부]         22 µs    0.9%
   └ post  v3 완료 → sendmsg           ~360 µs   15.8%
```

세 가지가 곧바로 읽힌다.

1. **계약이 보는 구간은 0.9% 다.** `span v3 < 30 µs` 를 통과해도 클라이언트는
   2.3 ms 를 기다린다.
2. **`post` 가 `span v3` 의 16 배다.** 원격 메모리를 읽는 것보다 그 완료를
   응답으로 바꾸는 것이 훨씬 비싸다.
3. 그런데 **그 대부분은 낭비가 아니라 공급 과잉의 결과다** — §4 참조.

## 1. 구간 정의와 계측 위치

전부 `EXT_RDMA_PROF=1` 게이트 아래에 있고, 꺼지면 분기 하나로 끝난다
(`extstore.c:1228`). 스탬프는 모두 `item_lock` **밖**이다 — 락 안에 넣으면
사이클 비용보다 임계구역 확장이 훨씬 비싸다.

| 구간 | 정의 | 스탬프 |
|---|---|---|
| `srv` | 소켓 read → sendmsg | `memcached.c` try_read_network / resp_finish |
| `que` | read → 이 명령의 처리 시작 | `c->t_read` → `resp->t_cmd` (resp_allocate) |
| `pre` | 명령 시작 → backend 진입 | 차분 `srv − que − bk` |
| `bk` | backend 진입 → sendmsg | `resp->t_enter` → resp_finish |
| `span v3` | backend 진입 → 응용 가시 완료 | `storage.c:470` / `storage.c:904` |
| `post` | v3 완료 → sendmsg | 차분 `bk − span_v3` |

`que` 는 **같은 `read()` 로 들어온 파이프라인 명령들이 서로를 기다린 시간**이다.
한 번의 read 가 256 개 명령을 실어오면 마지막 것은 앞의 255 개를 기다린다.

### span v3 내부

```text
GET  span v3 = admit + xfer + crypto + sync + 나머지
SET  span v3 = admit + xfer + crypto + sync + ret
```

| 성분 | 뜻 |
|---|---|
| `admit` | 진입 → 실제 post. 제출 배치(`ext_submit_batch=20`) 대기 |
| `xfer` | RDMA 왕복 |
| `crypto` | AES-256-GCM |
| `sync` | DMA advise. **coherent MR 이후 계측 하한**(0.02~0.05 µs, 이전 5.62) |
| `ret` | CQE → `ITEM_WFLIGHT` 해제 (SET 만) |

이 다섯은 **처음부터 계측돼 있었고 출력만 안 됐다.** 2026-08-04 에 obwatch 가
내기 시작했다.

## 2. `post` 의 정체 — 코드에 적혀 있다

```c
/* storage.c:461 — v2 (P2a) */
/* 이 cb 는 드레인 루프 안에서 돈다. 여기서 conn 을 돌려주면 드레인이 아직
 * bounce slot 과 window 회계를 정리하는 중에 이벤트루프에 재진입한다.
 * 주차해 둔다; 드레인 호출자가 루프 뒤에 flush 한다. */
STAILQ_INSERT_TAIL(&g_ret_head, (io_pending_t *)p, iop_next);
```

RDMA 완료 콜백은 응답을 보내지 않고 **큐에 주차**한다. 방출은 세 곳에서 한다:

```text
storage.c:624   reap tick 안 (ext_reap_every=8 마다).  단 g_skip_conn 로
                지금 처리 중인 커넥션은 제외한다
thread.c:530    pass 의 chain/pending flush 뒤 (무조건)
thread.c:536    드레인 스핀 루프 안, 32 건 거둘 때마다
```

**`g_skip_conn` 이 핵심이다.** 자기 자신의 커넥션이 아직 처리 중이면 재개에서
빠진다(재진입 방지). 그래서 파이프라인이 깊을수록 — 한 커넥션이 256 건을
연달아 내면 — **앞쪽 응답이 자기 뒤 255 건의 제출을 기다린다.**

그래서 `post` 는 깊이에 비례한다:

```text
pipeline    1      8     32     64
post     23.62  32.19  87.30  91.00 µs
```

**고정비가 아니다.** 처음에 "깊이 무관한 고정비" 로 읽었는데 틀렸다.

### 읽히는 것

**`span v3` 는 부하에 거의 불변이다** — 17.9 → 26.4 → 23.5 µs. 같은 구간에서
`post` 는 23.6 → 87.3 으로 **3.7 배** 늘었다.

> **계약이 재는 지표가 부하에 둔감하고, 안 재는 구간이 부하를 다 받는다.**
> 이것이 이 분해의 가장 실질적인 결과다.

`xfer` 는 8.13 → 15.06 에서 포화한다 — RDMA 자체는 견딘다.
`pre` 는 0.7~2.5 µs 라 파싱·해시는 잡음이다.

## 4. 줄일 수 있는가 — 있다. 코드 없이

| pipe | ops M | client avg | 10 M | 전 단계 대비 |
|---:|---:|---:|:-:|---|
| 128 | 12.668 | 1,178.2 | ✅ | 처리량 +65.3% / 지연 +148.4% |
| 256 | 13.242 | 2,277.6 | ✅ | 처리량 **+4.5%** / 지연 **+93.3%** |

**마지막 한 칸이 지연을 두 배로 내고 처리량을 4.5% 산다.**

```text
256 → 128 :  처리량 −4.3%,  클라이언트 지연 −48.3%
계약(10 M)은 128 에서도 통과한다 (12.668 M).
```

기전이 §2 와 맞는다 — 깊이를 반으로 줄이면 `post` 의 대기가 줄어든다.
처리량은 이미 128 에서 포화의 95.7% 라 잃을 것이 적다.

> **단, 이것은 서버 설정이 아니라 클라이언트 워크로드 특성이다.** 실제
> 애플리케이션이 256 깊이로 파이프라이닝하지 않으면 애초에 해당 없다.
> 벤치마크 수치를 위해 256 을 쓰고 있었다면 **"13.2 M @ 2.3 ms" 보다
> "12.7 M @ 1.2 ms" 가 더 나은 운영점**이다.

## 5. 계측 비용 — 4.2%

같은 바이너리에서 `EXT_RDMA_PROF` 만 뺀 무변수 A/B (2026-08-04):

```text
              ON          OFF        비용
GET-only    13.245 M    13.840 M    4.30%
1:9 혼합    10.926 M    11.393 M    4.10%
```

**기록된 계약 수치는 전부 천장보다 4.2% 아래다.** 13.397 M 게이트도 계측을
켠 채 낸 값이다 — **더 불리한 조건에서 두 조항을 동시에 통과**시킨 것이라
계약 주장에는 유리하다.

셀 간 비교는 전부 켠 채로 하면 유효하다. 절대값을 계약 기록 옆에 놓을 때만
이 4.2% 를 명시한다.

## 6. 아직 못 가른 것

`네트워크 + 클라이언트 큐잉`(pipeline=1 에서 162.92 µs)을 **전송**과
**클라이언트 처리**로 나누지 못했다.

- **`ping` 은 대리값이 안 된다.** IPoIB ICMP 왕복이 min 241 / avg 371 µs 로
  **우리 e2e(207 µs)보다 크다.** ICMP 는 오프로드 없는 느린 경로다.
- 루프백 대조(같은 커넥션 수, 네트워크만 제거)로 가를 수 있으나 미시행이다.
- 또는 genie 박스 측 계측.

**가르기 전까지 이 162.92 µs 를 "네트워크" 라고 부르지 않는다.**

## 7. 열려 있는 계측 결함 둘

설명하지 못한 것을 설명한 척하지 않기 위해 남긴다.

**① v2/v3 표본 카운트 역전.** 코드상 v3 는 v2 의 부분집합이다 — 같은 함수
(`extstore.c:1265`), 같은 `_Thread_local` 워커(`extstore.c:591`), 같은 리셋
경로(`extstore.c:1222`), v3 에 조건 하나 추가. 그런데 실측이
**842,032,108(v2) < 882,079,456(v3)** 였다. 모든 경로를 훑었고 못 찾았다.

**② `get_hits > cmd_get`.** 증가 지점이 전부 짝지어져 있는데
(`proto_parser.c:708-709`, `1235-1236`, `proto_bin.c:500-501`) 실측에서
**29,703,683 건 초과**했다. 창 시작에 고정된 초과이고 13.26 M/s 기준
2.24 초분이라 리셋 순회로는 설명이 안 된다.

**둘 다 처리량·span·srv/que/post 에는 영향이 없다** — 각각 다른 카운터이고
`get_misses` 는 0 이다. **`hit rate` 줄과 `커버리지` 줄만 못 믿는다.**
커버리지 검사를 v2 카운트에 남겨둔 것은 이 상황에서 오히려 다행이었다.

## 8. 측정 규율 — 이 캠페인에서 얻은 것

**창을 부하 시작 전에 연다.** 전속 중에 `stats reset` 이 돌면
`get_cmds`(`thread.c:1055`)와 `get_hits`(`thread.c:1064` memset)가 서로 다른
시점에 0 이 되는데 증가 쪽은 락이 없다(`THR_STATS_LOCK` no-op,
`memcached.h:989`). **실측 8.45% 오차를 봤다.**

**커버리지가 밴드(−1.0 ~ +0.2%) 밖이면 창 총계를 버리고 안정구간(10 s~)
초당 행을 쓴다.** `BD-PROF-ON-MIX-r1` 에서 검증됐다 — 총계 11.865 M,
행 10.961 M, 클라이언트 10.926 M. **경고 크기와 오차 크기가 같다.**

**`N = conns × pipeline` 은 상한이다.** memtier 가 배치를 다 받고 다음 배치를
내므로 상시 미결이 명목값보다 적다(실효 94.7~99.1%). **클라이언트 실측
latency 가 정본이고 `N/X` 는 교차검증이다.**
