# v4 재검 + sweep 재측정 계획

작성 2026-08-02. 계약은 달성됐다(`V4_RESULT.md`). 이 문서는 **남은 여유**와
**v2 시절 실험의 v4 재측정**을 다룬다.

## A. 재검 — 여유가 더 있나

계약 여유가 혼합 +1.0~1.2% 로 얇다. 다음 넷은 **근거가 있고 아직 안 봤거나,
락 지형이 바뀐 뒤 다시 봐야 하는 것**이다.

### A-1. flush 를 락 밖으로 — 재시도

전에 졌다(혼합 9.05 대 9.18). **그런데 그때는 refcount·stats 락이 그대로였다.**
락을 두 번 걷어낸 지금은 비용 쪽이 훨씬 작다.

```text
현재  SET span 21.68 = adm 0.56 + v2 6.72 + ret 14.39
      ret 가 SET span 의 66% 다
락 밖으로 뺐을 때  ret 0.81 (당시 측정)
```

**같은 손잡이가 상태에 따라 부호를 바꾸는 것을 이미 두 번 봤다**
(`reap=16`, `ext_setq_max`). 이것도 그럴 수 있다.

`git revert` 로 되돌려 놓은 `cc1a91d` 를 되살려 A/B 한다.

### A-2. reap / chain 재sweep

지금 값(`reap=12 chain=8`)은 **refcount 수정 전**에 고른 것이다. `reap=16` 이
그 후 부호를 바꿨으니 최적점이 움직였을 가능성이 크다.

```text
reap ∈ {8, 10, 12, 14}   chain ∈ {4, 8, 12}
span 예산이 GET 25.05 / SET 21.68 이라 위로 여유가 있다
```

### A-3. 평문 목적지를 응답 버퍼로 — 미시도

`C_get 2.469` 중 **평문/응답 할당이 0.154 (6.2%)** 다. GET 마다 평문 목적지를
캐시에서 할당하고 복호한 뒤 되돌려준다. 64 B 값이면 응답 버퍼로 직접 복호하면
그 한 쌍이 사라진다. **GET 이 혼합의 90% 라 지렛대가 있다.**

주의: `resp->wbuf` 크기와 chunked 경로를 확인해야 한다. 큰 값은 기존 경로로
떨어뜨린다.

### A-4. `admit_max` 재확인

64 는 체류가 47 이던 시절에 고른 값이다. 지금은 처리량이 올라 체류가 달라졌다.
**바인딩하는지부터 확인**하고, 안 하면 그대로 둔다.

## B. v2 실험의 v4 재측정

v2 시절 산출물은 `../memcached-1.6.42-port_v3/img/` 에 있다. 전부 **co-located,
v2 코드, span v2 기준**이므로 v4 와 직접 비교할 수 없다. 같은 축을 **off-box,
v4 코드, span v3** 로 다시 잰다.

### B-1. config matrix (`config-matrix-10s-20260724`)

```text
pipeline sweep   pipe ∈ {8, 16, 32, 64, 128, 256}
depth sweep      W   ∈ {8, 16, 24, 32, 40, 48, 64}
qp sweep         nqp ∈ {1, 2, 4, 8}
thread 조합      mcT ∈ {16, 20, 24, 28, 30}
```

**EXP-0 에서 pipeline 은 이미 v4 이전 코드로 쟀다**(6점). 인라인·체인이
들어간 지금은 곡선이 다를 것이므로 다시 잰다.

### B-2. thread × pipeline 민감도 (`sensitivity-thread-pipeline-20260727`)

```text
mcT sweep      pipe=256 고정, mcT ∈ {16, 20, 24, 28, 30}
pipeline sweep mcT=30 고정, pipe ∈ {32, 64, 128, 256, 384}
```

mcT=16 은 v4 에서 이미 쟀다(6.56 M). 나머지 점이 없다.

### B-3. qp × depth (`three-exp-20260727`)

```text
qpd1-p8    nqp × depth=1, pipeline=8
qpd1-p48   nqp × depth=1, pipeline=48
qpxdepth   nqp × W, W ∈ {128, 256}   ← v4 의 W 상한(64)과 다르다. 재설계 필요
plateau    처리량 고원 확인
```

**v2 의 `W=128/256` 은 지금 구조에서 의미가 다르다** — 인라인 post 와 체인이
들어가 창의 역할이 바뀌었다. 같은 숫자를 재현하지 말고 **같은 질문**
("동시성을 올리면 어디서 고원에 닿는가")을 v4 축으로 다시 던진다.

### B-4. frontier (`frontier-7point-20260724`)

계약선(10 M, span 30) 주변 7점. **v4 에서는 계약을 만족하는 점이 있으므로
"프론티어" 의 의미가 달라졌다** — 이제는 *여유가 얼마나 있는가* 를 그린다.

## C. 실행 순서

```text
1. A-1  flush 락 밖 재시도        A/B 2셀      가장 싸고 가장 유망
2. A-2  reap × chain 재sweep      6~12셀
3. A-3  평문 목적지 (코드)         A/B 2셀
4. B-1  pipeline / depth / qp     20셀 내외
5. B-2  mcT × pipeline            10셀
6. B-3  동시성 고원                8셀
7. B-4  frontier                  7셀
```

**A 가 먼저다** — 계약 여유를 두껍게 만드는 것이 sweep 표를 채우는 것보다
급하다. B 는 문서용 곡선이고 A 는 결과 자체를 바꾼다.

측정 위생은 `V4_RESULT.md` §6 을 따른다 — 추적기 1 개, perf 는 `-F 199` 10 초,
그리고 **genie 의 `NEXT: ariel` 확인 전에는 아무것도 건드리지 않는다.**
