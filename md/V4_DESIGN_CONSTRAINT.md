# v4 설계 제약 — span v3 avg < 30 µs 를 무엇이 가능하게 하는가

> **[v4 착수 시점 기록]** 이 문서는 그 시점의 기록으로 보존한다. 현재 운영값은
> [`OPTIMAL_RUNBOOK.md`](OPTIMAL_RUNBOOK.md), 최신 결과는
> [`V4_RESULT.md`](V4_RESULT.md) 다. **이 문서의 수치는 착수 전 추정·설계
> 논증이고 측정이 아니다.** 무엇이 맞고 틀렸는지는 맨 아래 §7 채점표에 있다.

작성 2026-08-01. v3 최종(`c0c5b4f`) 기준. v3 결과는
`../memcached-1.6.42-port_v3/` 에 그대로 보존돼 있다.

```text
목표   1:10 혼합 10 M ops/s  AND  GET-only 10 M ops/s
       두 워크로드 모두 span v3 avg < 30 µs      ← 정의가 v3 로 바뀌었다
```

---

## 1. 출발점 — v3 에서 현 운영점은 8배 초과다

`mcT=30 W=40 nqp=4 pipe=256`, off-box 실측:

| 워크로드 | 처리량 | span v2 | **span v3** | 판정 |
|---|---:|---:|---:|---|
| GET-only | 12.003 M | 25.26 µs | **243.99 µs** | v3 FAIL (8.1배) |
| SET-only | 4.161 M | 7.83 µs | **2372 µs** | v3 FAIL (79배) |
| 1:9 혼합 | 9.945 M | G 26.7 / S 15.4 | **G 323.7 / S 196.4** | v3 FAIL |

v2 로는 전부 통과였다. **정의를 바꾸자 하나도 통과하지 못한다.**

---

## 2. 그 시간이 어디 있는지 — 성분 분해

계측을 세 조각으로 쪼갰다(`extstore_prof_*_admit_avg_ns`, `*_ret_avg_ns`).
co-located, pipeline 64 × 64 conns:

```text
GET  v3  42.82 µs = admit  25.13  +  v2 17.69
                    └ 진입 → 실제 RDMA post (admission/queue)

SET  v3 294.96 µs = admit   0.54  +  v2  6.79  +  ret 287.64
                                                  └ CQE 관측 → WFLIGHT 해제
```

**두 경로의 병목이 다르다.**

- **GET**: 들어와서 post 되기까지 기다린다. W·ORD·bounce slot 이 없어
  extstore wait list 에 park 된다.
- **SET**: RDMA 는 6.79 µs 에 끝나 있는데, 그 완료가 `g_ret_head` 에 쌓인 뒤
  이벤트 루프가 `storage_flush_returns` 를 돌릴 때까지 287 µs 를 기다린다.
  **admit 은 0.54 µs 로 사실상 0** — pac 이 즉시 enqueue 하기 때문이다.

---

## 3. Little's Law 가 목표를 결정한다

```text
in-flight = throughput × latency
10 M ops/s × 30 µs = 300
```

**backend 안에 동시에 300건 넘게 있으면 목표는 산술적으로 불가능하다.**
지금은 GET 약 3,000건(243.99 µs × 12.003 M), SET 약 9,900건이다.
**10~30배를 줄여야 한다.**

### 3-1. 줄일 수 있는가 — 용량은 충분하다

무대기 서비스 시간(= 큐가 없을 때 한 건이 실제로 쓰는 시간)은 GET 17.69 µs 다
(그중 RDMA wire 11.00, crypto 0.52, 나머지 6.17).

```text
필요 in-flight = 10 M × 17.69 µs = 177 건        (워커 30개면 워커당 5.9)
그때 span      = 17.69 µs                        → 계약 통과
CPU 상한       = 30 워커 ÷ C_get 2.374 µs = 12.6 M/s   → 처리량 통과
```

**즉 목표는 달성 가능하다.** 막고 있는 것은 용량이 아니라 **큐**다.

### 3-2. W 를 줄이는 것만으로는 안 된다 — 대기열이 W 앞에 있다

`worker_post` 는 용량이 없으면 **wait list 에 park** 한다. 그 park 는
`storage_get_item` **이후**이므로 v3 에 그대로 잡힌다.

```text
v3 in-flight ≠ W × mcT
v3 in-flight = memcached 가 소켓에서 읽어 backend 로 넘긴 요청 수 전부
```

W=40 이든 4든, 클라이언트가 30,720 을 밀어넣고 memcached 가 그것을 다 읽어
`storage_get_item` 을 호출하면 **전부 v3 에 들어온다.** W 는 post 동시성을
정할 뿐 backend 체류량을 정하지 않는다.

> v2 기준 W sweep 이 "W=40 이 처리량 꼭짓점"이라 한 것은 유효하다. 다만
> **그 표의 span 은 전부 v2** 였고, v3 로 다시 재면 순위가 바뀔 수 있다.
> v4 에서 가장 먼저 할 측정이다.

## 4. 설계 선택지 — 그리고 각각이 실제로 무엇을 바꾸는가

### (A) SET 반환 경로 — **이것은 진짜 결함이다**

287.64 µs 가 "완료됐는데 응용에 안 보이는" 시간이다. RDMA 는 6.79 µs 에
끝났다. CQE 를 본 워커가 `g_ret_head` 에 넣고, 이벤트 루프가 다음에 그것을
비울 때까지 응답이 대기한다.

**고치면 클라이언트가 실제로 이득을 본다.** 지연이 옮겨 가는 것이 아니라
사라진다. v4 의 1순위다.

방향: 완료 콜백이 `item_lock` 을 잡을 수 있는 문맥이면 거기서 바로 WFLIGHT 를
풀고 응답을 쓴다. 지금 루프 레벨로 미룬 이유는 큐 상한 경로가
`do_store_item` 의 `item_lock(hv)` 아래에서 실행돼 같은 버킷이면 데드락이기
때문이다(`storage.c` 주석). **그 데드락을 피하는 다른 방법**을 찾는 것이 설계
과제다.

### (B) GET admission — **큐를 옮기는 것이지 없애는 것이 아니다**

backend 로 들어오는 요청 수를 300 으로 묶으면 v3 는 바로 30 µs 아래로
내려간다. 초과분은 소켓 버퍼에서 기다린다.

**정직하게 적는다: 클라이언트가 체감하는 지연은 그대로다.** Little's Law 는
협상 대상이 아니다 — 클라이언트가 30,720 을 밀어넣고 처리량이 10 M 이면
누군가는 30,420 건을 들고 있어야 하고, 그게 소켓 버퍼로 옮겨 갈 뿐이다.

그래도 할 값어치는 있다:
- 서버 메모리가 유계가 된다 (지금은 클라이언트 pipeline 이 서버 힙을 정한다)
- 꼬리 지연이 개선된다 (무한 큐는 p99 를 망친다)
- **v3 정의에 부합한다** — "backend 가 요청을 받은 뒤" 를 재는 것이므로,
  받지 않은 것은 애초에 span 밖이다

> **이 선택은 계약의 의미를 정한다.** v3 span 이 "backend 진입 후"라면
> admission control 은 정당하다. "클라이언트가 기다린 시간"이라면 정당하지
> 않다. 관리자 판단이 필요하다.

### (C) 서비스 시간 단축 — **유일하게 양쪽을 다 개선한다**

`in-flight = throughput × latency` 에서 세 값 중 둘을 고정하면 나머지가
정해진다. 클라이언트 부하를 유지한 채 클라이언트 지연을 줄이는 방법은
**처리량을 올리는 것뿐**이고, 처리량은 `워커 수 ÷ op당 CPU` 다.

```text
C_get 2.374 µs  →  30 워커에서 12.6 M/s 가 CPU 상한
```

CPU 분해에서 큰 항목:

| GET | µs/op | | SET | µs/op |
|---|---:|---|---|---:|
| 커널 인터럽트 진입 | 0.214 | | item 생명주기 | 1.921 |
| AES-GCM | 0.458 | | pac/storage | 0.872 |
| item_lock | 0.380 | | 해시 탐색 | 0.658 |
| TCP 소켓 복사 | 0.125 | | 락 | 0.613 |

이 방향은 느리지만 진짜다. 다만 **30 µs 계약을 여는 열쇠는 아니다** —
CPU 를 절반으로 줄여도 큐가 그대로면 v3 는 그대로다.

## 5. 그래서 v4 의 순서

```text
0. v3 정의로 기준선 재측정        지금 표는 전부 v2 기준이다
1. SET 반환 경로 (A)              진짜 결함. 287 µs. 클라이언트가 이득을 본다
2. admission 설계 결정 (B)        의미 판단이 먼저다 — 구현은 그 다음
3. 서비스 시간 (C)                병행. 계약과는 별개로 항상 옳다
```

**0 이 먼저다.** W sweep·형태 캠페인의 span 판정이 전부 v2 기준이라, v3 에서
어느 구성이 어디에 있는지 아직 모른다. 특히 **낮은 W 가 v3 에서 유리할
가능성** 이 크다 — v2 는 큐를 안 보여줬으므로 W 를 올릴수록 좋아 보였다.

## 6. 보존된 것

v3 의 모든 측정·문서·raw 는 `../memcached-1.6.42-port_v3/` 에 있다.
v4 는 그 최종 코드(`c0c5b4f`)에서 분기했고 v3 를 건드리지 않는다.

```text
v3 최종   GET-only 12.003 M / 1:9 혼합 9.945 M / SET-only 4.161 M
          span v2 기준 전부 통과, span v3 기준 전부 미달
          형태 캠페인 25셀 + W sweep 11셀 + CPU 분해
```

## 7. 채점 — 이 문서의 예측 중 무엇이 맞았나 (2026-08-03 추가)

착수 전 설계 문서라 예측을 담고 있다. v4 가 끝났으니 채점한다.

| 예측 | 결과 | 실제 |

| §2 SET admit 0.54 µs 는 사실상 0 | ✅ 맞음 | 최종 0.52 µs |
| §4-A "데드락을 피하는 다른 방법이 설계 과제" | ✅ 풀림 | `item_trylock` 으로 **질의**하고 마지막 재개만 보류 |
| §3-2 "**W 는 backend 체류량을 정하지 않는다**" | ❌ **틀림** | W 는 backend(`v2` 구간) 체류를 **정한다** — `W=8` 에서 6.12 로 눌렸다. 문장의 의도(= span v3 총합은 안 준다)는 맞고 표현이 틀렸다 |

### 미해결로 남긴 질문

§4-B 는 **관리자 판단이 필요하다**고 적고 끝났다:

> *"v3 span 이 'backend 진입 후'라면 admission control 은 정당하다.
> '클라이언트가 기다린 시간'이라면 정당하지 않다."*

**v4 는 이 질문에 답하지 않고 우회했다.** admission 을 조여 span 을 낮추는
대신 **대기 자체를 없앴다**(인라인 post·즉시 재개). `ext_admit_max=64` 는
운영값에 남아 있지만 **바인딩하지 않는다**(체류 11.5) — throttle 로 쓰이지
않는다.

그래서 질문은 여전히 열려 있다. **부하가 커져 admission 이 실제로 물리기
시작하면 다시 답해야 한다.**

### 이 문서의 수치가 V4_RESULT 와 다른 이유

```text
이 문서   GET-only 12.003 M / 243.99      genie 의 게이트 보고 (클라이언트 창)
EXP-0     GET-only 11.932 M / 242.29      ariel 의 서버 창 슬라이스
```

**같은 실험의 다른 창이다.** 0.6% 차이는 창 경계 탓이고, `V4_RESULT.md` 는
서버 슬라이스(EXP-0)를 정본으로 쓴다 — 성분 분해(`admit`/`v2`/`ret`)가
거기에만 있기 때문이다.
