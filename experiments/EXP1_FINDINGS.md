`8497c2bb`(S3·S2·W1) / `6e75a9e6`(S3b 이후) — 본문에 표기한다.

## 1. SET 반환 경로 — 끝났다

EXP-0 에서 SET-only span v3 의 **99.7%** 가 반환 경로였다(2371.84 / 2380.29).

`ext_setq_max=1` 이라 모든 SET 이 `storage_store_item_pac` 안에서, 즉
`do_store_item` 의 `item_lock(hv)` 아래에서 flush 한다. flush 4단계가 CQE 를
거두지만 그 자리에서 재개할 수 없다 — `return_cb` 가 같은 버킷의 `item_lock` 을
다시 잡기 때문이다.

**첫 시도는 틀렸다.** 루프 레벨에 재개를 넣었는데 거긴 pass 당 한 번이라
완료 하나가 그 pass 의 남은 SET 수백 개를 기다렸다. S3 가 반증했다
(`ret 2371.84 → 2390.28`, 무변화). 대조군 GET 이 기준선을 0.4% 안에 재현해
빌드가 아니라 수정이 틀렸음을 바로 알 수 있었다.

**고친 방법**: CQE 를 실제로 거두는 자리에서 재개하되, 데드락이 성립하는
**호출자가 잡은 그 버킷 하나**만 보류 목록으로 뺀다. 충돌 확률은
`1/2^item_lock_power` 라 실제로는 아무것도 안 밀린다. `conn_worker_readd` 가
`event_active` 로 예약하므로 재진입도 없다.

```text
              수정 전 (EXP-0)          S3b (수정 후)
SET-only    Sv3 2380.29 / ret 2371.84  →  Sv3   8.77 / ret 0.14
혼합 SET    Sv3  188.75 / ret  173.11  →  Sv3  16.55 / ret 0.18
처리량      4.133 / 10.055 M           →  4.115 / 9.830 M   (drift 안)
```

커밋 `3a50784`.

## 2. GET admit — 여섯 축을 다 봤다

### 축별 결과

| 축 | 바꾼 것 | 결과 | 왜 |
|---|---|---|---|
| `submit_batch` | 20 → 4 | adm 219.06 → **217.48** | pipe=256 에선 무관. 배칭은 pipe=8(파킹 불가)에서만 지배적이었는데 고부하로 잘못 연장했다 |
| `W` | 40 → 64 | 총합 242.21 → **241.53** | park/op 7 → 2.82, adm ↓16.2, **v2 ↑15.5**. 대기가 wait list 에서 창으로 옮겨갈 뿐 |
| `-R` | 1024 → 32 | 혼합 9.830 → **8.473 M** | span 316 → 190 이지만 처리량이 먼저 게이트를 깬다 |
| 연결 수 | 120 → 30/60 | 60 이 최적 | 60: 혼합 10.149 M / 164.81. 30: busy 24.0 으로 스레드를 못 먹인다 |
| pipeline | 256 → 32 (conns 60) | **5.086 M** | 방문당 요청이 줄어 CPU/op 폭증 |
| **admission** | 상한 12 | **계약 충족** | 아래 |

**앞의 다섯은 전부 제시량을 움직인다.** 그런데 서버 몫 비율(9~15%)이 안 바뀌어
처리량과 체류가 **같이** 줄었다. 계약선을 못 넘는 이유가 이것이다.

### 링크가 문제를 정의한다

genie 측정: `-t 1 -c 1 --pipeline=1 → 5,623 ops/s → 왕복 177.8 µs`.
클라이언트는 포화가 아니다(스레드당 0.34~0.62 코어). **IPoIB 링크다.**

```text
필요 in-flight  10 M × 177.8 µs = 1,778 건   ← 링크가 정하는 물리적 하한
목표 backend    10 M ×  30 µs   =   300 건
```

**질문은 "몇 건이 떠 있나"가 아니라 "어디서 기다리나"다.**

### admission 축 — 유일하게 계약을 통과한다

`ext_admit_max`: 워커가 물고 있는 비동기 요청이 상한에 닿으면 `conn_new_cmd`
에서 파싱을 멈춘다. 이미 읽어둔 소켓 버퍼는 그대로 남아 다시 읽지 않는다.

| admit | GET-only | Gv3 | 1:9 혼합 | Gv3 | Sv3 | 혼합 여유 | busy |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 10 | 6.161 M | 21.02 | 5.480 M | 23.57 | 13.42 | +6.43 | 29.9 |
| **12** | **6.801 M** | **23.19** | **6.036 M** | **26.44** | **14.92** | **+3.56** | 29.9 |
| 14 | 7.343 M | 25.41 | 6.545 M | 29.24 | 15.61 | +0.76 | 29.8 |
| 16 | 7.706 M | 27.63 | 6.794 M | 32.53 | 16.23 | −2.53 | 29.9 |
| 24 | 8.955 M | 36.67 | 7.635 M | 45.05 | 17.41 | −15.05 | 29.9 |
| ∞ | 11.880 M | 243.76 | 9.830 M | 316.24 | 16.55 | −286 | 29.9 |

**운영점은 `ext_admit_max=12`** 다. A14 도 통과하지만 여유 0.76 µs 가 bed
drift 1.4% 안이라 운영값이 못 된다.

**혼합이 항상 먼저 걸린다** — GET-only 는 A16 에서도 27.63 으로 통과한다.

### 기전 정정 — 상한은 실제로 안 닿는다

```text
A10   체류 130 (상한 300)   busy 29.9
A24   체류 328 (상한 720)   busy 30.0
```

**CPU 가 묶고 있지 상한이 묶는 게 아니다.** 실제 기전은 *yield 를 자주 시켜
방문당 배치가 작아지고 → CPU/op 이 올라 서버가 느려지고 → 큐가 짧아진다* 이다.
"큐를 상한에서 자른다"는 내 첫 설명은 틀렸다.

## 3. 벽 — 연결 방문당 26 µs

EXP-0 의 pipeline 곡선 6점 최소제곱(잔차 ±0.2 µs, n 을 32배 바꾸는 동안):

```text
CPU/op = 2.261 + 35.86 / n          n = 연결 방문당 요청 수
```

admission 의 yield 경로는 완전한 방문보다 싸서 유효 계수가 **26.1** 이다
(A10 실측 4.87 = 2.261 + 26.1/10).

```text
base 2.261 µs   → 방문 비용이 0 이어도 CPU 상한은 30 / 2.261 = 13.27 M/s
방문 26.1 µs    → 10 M 예산 3.0 µs 는 n ≈ 35 를 요구
                  n 35 × 30 워커 = 체류 1,060  →  span 106 µs      ✗
방문  5 µs 라면 → n ≈ 7  → 체류 210  →  span 21 µs                 ✓
```

**방문 비용을 26 → 5 µs 로 줄이면 계약이 열린다.** 여섯 축이 전부 이 벽에서
막혔고, 이것 말고 다른 길은 이 캠페인에서 찾지 못했다.

방문 비용의 정체는 epoll 복귀 · `read` · `drive_machine` · 응답 조립 ·
`writev` 왕복이다. **분해는 낮은 pipeline 에서 재야 보인다** — pipe=256 은
방문 비용이 CPU/op 의 6% 지만 pipe=8 은 **66%** 다. 그 perf 를 요청해 뒀다.

## 4. 별건 — badcrc (v4 이전부터 있던 것)

EXP-0 트레이스를 셀별로 가르자 드러났다. **혼합에서만, 부하에 비례한다.**

| 워크로드 | badcrc | GET 대비 |
|---|---:|---:|
| GET-only 6셀 | **0** | 0.0000% |
| 혼합 pipe=8 | 142 | 0.0002% |
| 혼합 pipe=256 | 60,209 | **0.0250%** |
| SET-only 3셀 | **0** | 0.0000% |

**원인**: 상류 extstore 는 **페이지** 단위로 재활용하고 `page_version` 으로
낡은 읽기를 걸러낸다. 이 포트는 **슬롯** 단위로 재활용하면서 버전을 올리지
않는다(`extstore.c:534` 주석이 "이 포트에는 페이지 재활용이 없으므로"라고
적고 있다). 그래서 `extstore_check` 가 항상 통과하고 **상류의 안전망이 무력하다.**

```text
1. GET  loc L 을 복사하고 RDMA READ post. hdr_it 에 refcount 를 쥔다
2. SET  item_replace → storage_delete(old_it) → extstore_free_loc(L)
                                                  ↑ refcount 를 보지 않는다
3. L 이 자유목록으로 → 다음 SET 이 L 에 원격 WRITE
4. 1번의 READ 가 새 바이트를 물어옴 → GCM 태그 불일치 → badcrc → MISS
```

값이 클라이언트로 새지는 않는다(badcrc 는 MISS 처리). 그러나 **있는 키가
조용히 MISS 로 돌아간다.** 우리 둘 다 못 봤다 — `err5` 집계에 badcrc 가 없고
hit 율 0.025% 는 "100%"로 반올림된다. **v3 의 계약 달성치도 이 조건에서 잰
값이다.**

**수정**: 회수를 unlink 시점이 아니라 `item_free` 로 옮긴다. GET 이 이미
`hdr_it` refcount 를 쥐므로 그것만으로 보호가 성립하고, `do_item_remove` →
`refcount_decr == 0` → `item_free` 가 유일한 소멸 경로다. 호출처가 9군데라
하나씩 지우면 빠뜨리므로(실제로 `proto_parser`·`proto_bin`·`proto_proxy` 7군데를
처음에 놓쳤다) `STORAGE_delete` 매크로 **한 곳**에서 막았다. 헤더를 할당 시
0으로 채워 `len==0` 을 "loc 없음" 표시로 삼아 이중 회수를 막는다.

브랜치 `badcrc-fix` (`a335a50`). **아직 배포 안 했다** — 회수를 늦추면 슬롯
압력이 바뀌어 A 축 측정에 섞인다.

## 5. 이 캠페인에서 내가 틀렸던 것

기록해 둔다. 같은 실수를 반복하지 않기 위해서다.

| 틀린 것 | 무엇이 잡았나 |
|---|---|
| SET 재개를 루프 레벨에 넣으면 된다 | S3 (`ret` 무변화). 대조군이 살아 있어 빌드가 아님을 바로 알았다 |
| admit 은 submit 배칭이다 | S2 (219 → 217). 저부하 관측을 고부하로 연장한 것 |
| `in-flight ∝ conns` | conns=30 (4배 감소에 체류는 2.6배만) |
| 연결을 줄여도 처리량은 안 떨어진다 | conns=30 (busy 24.0, −18%) |
| admission 은 처리량을 1.9% 만 먹는다 | A10 off-box (−48%). **co-located 자체확인에서 연결 위상을 안 맞췄다** |
| admission 이 큐를 상한에서 자른다 | 체류가 상한에 닿지 않는다 (130/300, 328/720) |
| 244 µs 는 클라이언트일 것이다 | genie 의 단일요청 왕복 177.8 µs 측정 |

**delta 실험이라도 형태(연결 수·워커당 연결)는 맞춰야 한다** — 다섯 번째가
가장 비쌌다.
