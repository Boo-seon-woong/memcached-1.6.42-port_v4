## 상한 제거 후 재탐색 (2026-07-28)

`EXT_QP_MAX=4`, `worker_window<=64`, `EXT_READ_SLOTS<=64`, `drain_spin<=4096`,
ORD 16 하드코딩, batch 32 하드코딩이 모두 제거된 binary로 위 캠페인이
도달하지 못했던 영역만 골라 재측정했다. 문서 상단의 129점은 다른 boot이므로
직접 비교하지 않고, **같은 세션 앵커**를 먼저 잡고 그 값과만 비교한다.

### 왜 이 후보들인가

기존 최고점(`mcT=14, CPU 14/10, W=36, QP=4` → 7.479M, avg 25.3us)에서:

```text
실제 in-flight = 7.479M x 25.3us = 189
window 상한    = 14 x 36 = 504          -> W는 37%만 사용, 바인딩 아님
server CPU     = 7.479M x 1.9us = 14.2 core-s/s on 14 cores = 101%  -> 포화
```

즉 막고 있던 것은 상한이 아니라 **server CPU**다. 그래서 (a) 최적점이 정확히
캡에 앉아 있던 QP 축, (b) 미탐색 CPU 배분, (c) W 확장, (d) batch 축만 골랐다.

### 결과

### 판정: 제거된 상한 중 throughput을 올리는 것은 없다

- **QP>4**: 첫 측정 QP=6이 7.325M(앵커 대비 +3.8%)로 보였으나 **재현되지
  않았다**(6.658, 7.136). QP=6 3회 스프레드 10%인 반면 앵커 QP=4는 2회
  스프레드 0.3%다. 평균으로는 차이가 없다. 이는 앞선 `ORD x QP` 비율 실험과
  정합적이다 — W=36이 먼저 바인딩되므로(QP=4에서 이미 ORD x QP = 64 > 36)
  QP를 늘려도 wire 동시성이 변하지 않는다.
- **W 확장**: W=44부터 avg가 30us를 넘는다. throughput은 7.2M대로 평평하고
  latency만 오른다. 기존 캠페인의 "W=42부터 avg>30" 관측과 일치한다.
- **CPU 배분**: 14/10이 최적이다. server를 늘리면 client 공급이 줄어 CPU/op가
  오히려 나빠진다(15/9에서 1.998, 17/7에서 2.276).
- **batch**: 32/64/128 사이에 차이가 없다. W=36이 먼저 걸려 한 번의 post에
  32개를 채울 일 자체가 드물다.

### 결론

co-located 구성의 throughput 상한은 **약 7.0~7.3M Ops/s**이고 그 지배 요인은
server CPU다. 상한 제거는 탐색 공간을 열었지만 그 안에 더 높은 지점은 없었다.
throughput을 더 올리려면 knob이 아니라 **per-op CPU를 낮추는 코드 작업**이
필요하다. 운영점은 기존과 동일하게 유지한다.

CPU 배분 분석으로 co-located 이론 상한을 추정하면:

```text
Cs = T x 1.9us,  Cc = T / 0.9M,  Cs + Cc = 24
-> T ~ 8.0M/s,  Cs ~ 15,  Cc ~ 9
```

실측 7.0~7.3M은 이 추정의 88~91%로, 남은 여유가 크지 않다.

## Client 공급 능력 실측과 10M 성립 여부 (2026-07-28)

지금까지 "client가 몇 core면 얼마를 공급할 수 있는가"를 측정한 적이 없었다.
server가 병목이 되지 않도록 **stock memcached**(RAM, ~0.9us/op)를 서버로 두고
client core 수만 바꿔 memtier의 공급 상한을 쟀다.

| client cores | pipeline | Ops/s | core당 |
|---:|---:|---:|---:|
| 4 | 64 | 3.674M | 0.919M |
| 6 | 64 | 5.150M | 0.858M |
| 8 | 64 | 6.679M | 0.835M |
| 10 | 64 | 8.641M | 0.864M |
| 4 | **128** | **4.283M** | **1.071M** |
| 4 | 256 | 4.209M | 1.052M |

거의 선형이며 pipeline을 올리면 core당 0.86M -> **1.07M**까지 오른다(P=128이
무릎, 256은 이득 없음). 기존 캠페인이 P=80 위주였으므로 client를 덜 짜고
있었다.

### 10M 성립 여부

```text
server : 10M x 1.9us/op   = 19.0 cores
client : 10M / 1.07M      =  9.3 cores
합계                       = 28.4 cores   > 24
```

**약 4.4 core 부족하다.** 즉 co-located 구성에서 10M은 산술적으로 성립하지
않는다. 그리고 부족분의 주체는 client가 아니라 server다 — client는 9 core면
9.6M을 공급할 수 있어 10M에 근접하지만, 남는 15 core로 server가 낼 수 있는
것은 약 7.9M뿐이다.

### server core를 늘리면 안 되는 이유

단순 모델(`Cs x 0.526 = (24-Cs) x 1.07`)은 server 16 / client 8에서 8.46M을
예측했지만 실측은 그 반대였다.

| 설정 | Ops/s | CPU us/op |
|---|---:|---:|
| CS=14 client 10, P=80 | 7.453 | 1.772 |
| CS=15 client 9, P=128 | 6.896 | 2.074 |
| CS=16 client 8, P=128 | 6.685 | 2.206 |
| CS=17 client 7, P=80 | 6.622 | 2.276 |

**CPU/op가 상수가 아니다.** client를 조일수록 server의 per-op 비용이 오른다
(1.77 -> 2.28us). 늘린 core가 나빠진 효율에 그대로 상쇄되어 총량이 오르지
않는다. 각 지점의 실측 CPU/op로 용량을 다시 계산하면
`14/1.772=7.90M`, `16/2.206=7.25M`으로 오히려 감소한다.

### 과잉 offered load의 비용

pipeline만 분리해 보면 P=128이 P=80보다 나쁘다.

| pipeline | Ops/s | CPU us/op | wait_enq |
|---:|---:|---:|---:|
| 80 | 7.453 | 1.772 | 805M |
| 128 | 7.307 | 1.831 | 1171M |

window(W=36)가 흡수할 수 있는 양을 넘는 요청은 wait list에 park되었다가
재post된다. 74.5M GET에 park이 805M회 — 요청당 약 11회다. pipeline을 60%
올리면 park이 45% 늘고 그만큼 CPU를 먹는다. **client를 더 짜는 것은 server의
낭비를 늘릴 뿐이다.**

### 측정 분산에 대한 주의

동일 설정(`CS=14, mcT=14, mtT=10x13, P=80, W=36, QP=4`) 10초 단발 run이
7.059 / 7.041 / 7.453 M/s로 나왔다. 스프레드 약 6%다. 이보다 작은 차이는
반복 없이 순위화하지 않는다.

### 결론

co-located 상한은 **약 7.3~7.5M Ops/s**이고, 늘릴 방법은 core 재배분이 아니라
per-op CPU를 낮추는 것뿐이다. 10M을 목표로 하려면 client를 이 box 밖으로
빼서 24 core 전부를 server에 주어야 하며, 그 경우에도 `10M x 1.9us = 19 core`가
필요하므로 성립 가능하다(현 CPU/op 기준 여유 5 core).

## 30 vCPU guest 실험: server core는 확장되지 않는다 (2026-07-28)

"server 20 core면 10M이 되지 않나"를 확인하기 위해 guest를 **30 vCPU**로
재기동하고(host 32 core), client를 정확히 10 core로 고정한 채 server core만
늘렸다. binary/설정은 동일하고 `W=36, QP=4, spin=1024`다.

먼저 오염 검사: 30 vCPU 안에서 24 vCPU 시절 최고 설정(server 14 / client 10)을
그대로 재현하면 7.153M/s, CPU 1.841us/op, steal 0.1s로 24 vCPU 범위

**core를 14에서 20으로 43% 늘려도 throughput은 7.1~7.5M로 평평하다.**

### 함의: 10M 계획의 전제가 무너진다

앞 절에서 `10M = server 19 core x 1.9us/op`로 계산했지만, 그 계산은
**core당 0.53M이 유지된다**는 가정 위에 있었다. 실측은 그 가정을 부정한다.
현 코드로는 20 core에서도 7.5M 언저리이며, core를 더 준다고 10M에 접근하지
않는다.

따라서 이전에 검토한 두 방향의 기대값을 모두 하향해야 한다.

- guest 30 vCPU(20 server / 10 client): **실측 7.5M** — 예측 10.6M과 크게 다름
- guest 21 vCPU + client를 host로: server 21 core가 근거였으나 core당 효율이
  이미 무너지는 구간이므로 11.1M은 성립하지 않는다. 경로(virtio) 작업을 하기

## 근본 원인: 물리 코어 부족과 per-op CPU 분해 (2026-07-28)

### worker 수를 늘려도 안 되는 이유는 하드웨어다

host는 **AMD EPYC 9124 — 물리 16 코어, SMT2, 논리 32**다. L3는 64MiB가 4
인스턴스(CCX당 16MiB)인데 guest는 8MiB 1개짜리 플랫 토폴로지로 본다.

| 구성 | 총 thread | 물리 코어당 |
|---|---:|---:|
| server 14 + client 10 | 24 | 1.5 |
| server 18 + client 10 | 28 | 1.75 |
| server 20 + client 10 | 30 | 1.9 |

**16 thread를 넘으면 늘어나는 것은 코어가 아니라 하이퍼스레드다.** 두 worker가
한 물리 코어의 L1/L2와 실행 유닛을 나눠 쓰므로 각자 느려진다. 이것이 모든
관측을 설명한다: core당 처리량 0.53 -> 0.38M, 유휴 core 무효, drain spin 무효,
그리고 `assoc_find`(메모리 지연에 민감한 lock 없는 포인터 추적)가 6.29% ->
12.93%로 정확히 2배가 된 것.

따라서 현 상한은 소프트웨어 한계가 아니다:

```text
16 물리코어 / 1.772us/op = 9.03M/s   (서버가 칩 전체를 독점할 때)
client가 약 1/3을 가져가면          ~7.5M   <- 실측과 일치
```

### per-op CPU 분해 (mcT=14, 프로파일 hz=499)

| stage | caller | 비중 |
|---|---|---:|
| `ioctl` | `execute_ioctl` = `ibv_advise_mr` | **11.41%** |
| `sendmsg` | `transmit` | 11.48% |
| `pthread_mutex_lock` | `item_get` 2.19 + `item_remove` 1.51 (item lock) | 12.04% 중 3.7%+ |
| `assoc_find` | (lock 없음) | 6.29% |
| `__read` | TCP 수신 | 4.86% |
| `worker_post` + `mlx5_poll_cq_v1` | RDMA 경로 | 5.27% |

RDMA 경로 자체는 5% 남짓이다. 비용은 SEV DMA sync, TCP, item lock에 있다.

### DMA sync는 제거할 수 없다 (실측)

bounce/staging은 `/dev/snp_shared`의 decrypted·cache=wb 페이지이므로 SWIOTLB를
타지 않고 NIC이 직접 쓴다. x86 DMA가 캐시 코히런트라면 `SYNC_FOR_CPU` advise가
불필요할 수 있다는 가설을 `EXT_SKIP_DMA_SYNC`로 검증했다.

결과: sync를 끄면 **GET 500만 건이 전부 실패**한다(badcrc/miss). 기준선은
7.204M/s, bad=0으로 정상이다. 즉 이 advise는 장식이 아니라 데이터 가시성에
필수이며, v1 selftest가 남긴 경고("SWIOTLB sync missing from mlx5_ib")와
일치한다. **11.4%는 SEV 기밀 컴퓨팅의 비용이고 유저스페이스에서 제거할 수
없다** — 없애려면 v1이 보류한 coherent-MR 커널 트랙이 필요하다.

### 남은 감축 후보

| 대상 | 비중 | 성격 |
|---|---:|---|
| DMA sync ioctl | 11.4% | 커널 트랙(coherent-MR) 없이는 불가 |
| TCP transmit | 11.5% | 구조적. client가 같은 박스에 있는 한 존재 |
| item lock (`item_get`/`item_remove`) | 3.7%+ | **v2에서 재검토 여지 있음** — stub은 GET 중 refcount 외에는 불변 |
| `assoc_find` | 6.3% | hash 구조. 코어를 늘릴수록 악화 |

### 결론

- 이 호스트에서 **10M은 성립하지 않는다**: `10M x 1.6us/op = 16 코어`이므로
  per-op CPU를 1.772 -> 1.6 이하로 낮추고 **동시에 client를 박스 밖으로 완전히
  빼야** 겨우 도달한다. client가 온보드면 서버 몫이 11~12 코어라 1.15us/op가
  필요하며 비현실적이다.
- guest는 **24 vCPU로 되돌렸다**. 28/30은 하이퍼스레드만 늘려 손해다.
- 성능 작업을 계속한다면 방향은 코어가 아니라 per-op CPU이고, 유저스페이스에서
  손댈 수 있는 것은 item lock과 assoc_find 정도(합쳐 10%)다.
