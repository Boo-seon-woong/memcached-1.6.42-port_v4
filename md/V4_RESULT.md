# v4 결과 — span v3 계약 달성

작성 2026-08-02. v3 는 `../memcached-1.6.42-port_v3/` 에 동결돼 있다.

```text
계약   1:10 혼합(SET:GET) 10 M ops/s  AND  GET-only 10 M ops/s
       두 워크로드 모두 GET span < 30 µs  AND  SET span < 30 µs
       span 정의는 v3 — backend 진입에서 응용 가시 완료까지
```

---

## 최종 게이트

재검(§7) 뒤 값이다. 추적기 1 개, 아무것도 동승하지 않음.

```text
GET-only  13.405 M   span 25.99 = adm 3.61 + v2 22.38                  ✓ ✓
1:9 혼합  10.777 M   GET 19.87 = 7.11 + 12.77                          ✓ ✓
                     SET  8.97 = 0.54 + 7.50 + 0.93                    ✓ ✓
```

재검 전 120 초 게이트(참고, 창 두 번):

```text
GET-only  12.393 M / 25.05    SET-only 5.434 M / 7.67
1:9 혼합  10.122 M / G 20.41  S 21.68        10.094 M / G 20.45  S 21.70
```

**두 워크로드 모두 처리량과 span 을 만족한다.**

운영값:

```text
ext_admit_max=64  ext_reap_every=12  ext_post_chain=8  ext_setq_max=1
ext_submit_inline  ext_submit_batch=20  W=40  nqp=4  mcT=30  -R 1024
```

여유는 혼합 처리량이 **+7.8%** 다. 재검 전에는 +1.0~1.2% 로 bed drift 1.4% 와
같은 자릿수였는데, §7 의 두 수정이 그것을 두껍게 만들었다.

출발점 대비:

```text
              혼합       GET span   SET span
v3 정의 직후   9.83 M     316.24     188.75     둘 다 위반
v4 최종       10.78 M      19.87       8.97     둘 다 통과
```

**span 15 배 감소, 처리량 +9.6%.**

## 1. 무엇이 문제였나 — 대기 세 겹

span 정의를 v2 → v3 로 넓히자 계약이 8 배 초과로 깨졌다. **정의가 성능을 바꾼
것이 아니라 원래 있던 대기가 계측 안으로 들어왔다.** 증거: 클라이언트가 보고한
SET 지연이 7.45 ms 인데 v2 는 7.8 µs 라고 했다.

v3 로 GET 에 추가된 구간은 전부 **워커 전용 로컬 작업**이다 — TLS 캐시 할당,
io_cache 할당, 빈 iov, 구조체 복사, 큐 삽입, 카운터 증가. 200 ns 면 끝날 일에
25 µs 가 붙어 있었다:

| 대기 | 크기 | 원인 | 수정 |
|---|---:|---|---|
| 제출 | 9.91 µs | 연결의 읽기 버퍼를 다 파싱해야 io_queue 제출 | 파싱 즉시 post |
| 완료 관측 | 31.56 → 5.52 | CQE 가 pass 끝까지 **폴링조차 안 됨** | post 자리에서 수거 |
| SET 재개 | 25.48 µs | 거두고도 재개를 다음 pass 로 미룸 | 마지막 재개만 보류 |

**SET 이 답을 갖고 있었다.** pac 의 admit 은 처음부터 0.5~0.7 µs 였다 —
큐에 넣자마자 그 자리에서 flush 하기 때문이다. GET 경로만 상류 memcached 의
io_queue 배칭을 물려받고 있었다.

## 2. 처리량은 락에서 나왔다

span 을 연 뒤 혼합은 9.2 M 이었다. 나머지는 전부 **경합**이었다:

| 수정 | 무엇이었나 | 효과 |
|---|---|---|
| 아이템 카운터 샤딩 | SET 1 건이 공유 캐시라인을 **10 번** 갱신. stub 이 전부 같은 slab class | SET-only +27% |
| refcount 원자화 | GET 이 `item_lock` 을 **두 번** 잡음. 두 번째는 `--refcount` 가 원자가 아니어서 | 두 워크로드 +8.5% |
| 워커 통계 락 제거 | GET 1 건이 `stats.mutex` 를 **두 쌍** 잡음 | 혼합 +0.6% → 계약 |

셋 다 **원자 연산이거나 락이 필요 없는 데이터인데 30 워커가 같은 줄을
두드리던 것**이다. 프로파일에서 `pthread_mutex` 가 계속 1 위였고, 세 번에
걸쳐 `C_get` 2.754 → 2.469, 락 0.504 → 0.291 로 내려갔다.

## 3. 코드 변경

```text
3a50784  SET 반환 경로 — 완료를 거둔 그 pass 에서 재개
185ec64  badcrc — 원격 슬롯 회수를 unlink 에서 item_free 로
3edbd11  ext_submit_inline — 파싱 즉시 post, io_queue 우회
9d4a924  post 자리 수거 — 파싱 중인 연결과 자기 자신을 제외
adb82a0  item_trylock — 락 보유를 추측하지 않고 질의
460d326  마지막 재개만 보류 — resps_suspended > 1 이면 안전
30ae0a4  ext_reap_every — 수거를 N 건마다로 상각
6277c37  ext_post_chain — post 를 N 건씩 묶어 QP 스핀락을 1/N 로
c580468  ext_setq_max 를 stats settings 에 노출
b75a61d  아이템 카운터를 워커별로 샤딩
6ba0c55  refcount 원자화 — item_remove 가 0 일 때만 잠근다
d88ea82  워커 통계 뮤텍스 제거
```

### badcrc — v4 이전부터 있던 정합성 결함

혼합에서 **있는 키가 조용히 MISS 로 돌아가고 있었다**(pipe=256 에서 GET 의
0.025%). 상류 extstore 는 페이지 단위로 재활용하고 `page_version` 으로 낡은
읽기를 걸러내는데, **이 포트는 슬롯 단위로 재활용하면서 버전을 올리지
않는다**(`extstore.c:534`). `storage_delete` 가 unlink 시점에 loc 을 회수해
읽는 중인 원격 메모리를 다음 SET 이 덮어썼다.

회수를 `item_free` 로 옮겼다 — GET 이 이미 refcount 를 쥐므로 그것으로 보호가
성립한다. 호출처가 9 군데라 `STORAGE_delete` 매크로 한 곳에서 막았다.

**우리 둘 다 못 봤다**: `err5` 집계에 badcrc 가 없었고 hit 율 0.025% 는
"100%" 로 반올림된다. v3 의 계약 달성치도 이 조건에서 잰 값이다.

## 4. 측정하고 기각한 것

| 시도 | 결과 |
|---|---|
| EVP 배관 | 마이크로벤치 최선 −3.1% → CPU/op 의 0.34% |
| `item_lock` 배열 축소 (15→10) | **−4% 악화** |
| IPoIB connected 모드 | 커널이 거부 (`I/O error`) |
| SWIOTLB 바운스 | op 당 ~400 B ≈ 40 ns |
| rx-usecs coalescing | 처리량 불변 (이미 패킷당 1 인터럽트) |
| `-R` 32 | 처리량·span 둘 다 악화 |
| `ext_setq_max` 4 | 혼합 +3%, 두 span 초과. SET 밀도 10% 라 배치를 못 채운다 |
| `admit_max` + `chain` 조합 | 상한이 체인 슬롯을 세어 과도하게 조인다 |
| `mcT` 16 (물리 코어 독점) | 6.56 M. vCPU 당 효율 +21% 지만 코어 수가 이긴다 |
| flush 를 락 밖으로 | 혼합 9.05 대 9.18. SET span 은 8.6 으로 좋아지나 처리량을 낸다 |
| `reap` 16 (refcount 후) | 처리량 불변, GET span 31.16 초과. 같은 손잡이가 상태에 따라 반대 |

## 5. 남은 여유와 다음 표적

혼합 여유는 §7 뒤 **+7.8%** 다. 아래는 `C_get 2.469`(§7 이전) 기준의 남은
항목이고, `resp_allocate` 는 §7 에서 처리했다:

```text
[k] __irqentry   0.241   9.8%   NIC 인터럽트. coalescing 은 기각됨
락 (item_lock)   0.291  11.8%   조회 1 쌍. 해시 버킷과 합치면 줄지만 큰 변경
해시             0.173   7.0%   assoc_find + prefetch + murmur
resp_allocate    0.123   5.0%   ← §7 에서 처리 (memset 1192 → 164 B)
EVP 배관         0.120   4.9%   기각됨
평문 목적지 할당  0.012   0.5%   기각 — 크기가 없다
```

**남은 것 중 크기가 있는 건 `item_lock` 조회 한 쌍(0.291)과 커널 인터럽트
(0.241)뿐이다.** 전자는 락 배열을 해시 버킷과 합쳐야 줄고(큰 변경), 후자는
coalescing 이 이미 기각됐다.

기계 한계도 적어둔다:

```text
호스트  AMD EPYC 9124  물리 16 코어 / 32 스레드
guest   -smp 30 (관리자 확정, 변경 없음)
        vCPU 는 호스트 0..29 에 1:1 핀. SMT 짝 (0,16)…(15,31)
        → 14 코어가 SMT 공유, 2 코어 단독

물리 코어 1 개 단독 0.410 M/s,  SMT 2 스레드 0.604 M/s  (배율 1.47)
현재 배치의 천장 = 14×0.604 + 2×0.410 = 9.27 M  ← 이 값은 개선 전 기준이다
```

**절대값은 낡았지만 비율은 살아남았다.** §9 에서 같은 1.47 배율로 세운 모형이
`mcT` 축 네 점을 1% 안에서 맞힌다 — 천장을 SMT 가 정한다는 결론은 그대로고,
현재 빌드의 천장이 13.3 M 으로 올라갔을 뿐이다.

```bash
pgrep -c -f 'shape-trace-v[3].sh'    # 자기 명령줄엔 v[3] 이라 안 맞는다
```

perf 는 커널 버전을 확인해야 한다. guest 는 `6.16.0-snp-guest` 인데
`/usr/bin/perf` 는 6.8 래퍼라 거부한다. 실제로 도는 것은
`/usr/lib/linux-tools/6.8.0-111-generic/perf` 다. **새 계측 스크립트는 창에
걸기 전에 스모크로 샘플 수를 확인한다** — stderr 를 버린 채 조용히 실패해서
창 하나를 통째로 날린 적이 있다.

raw 는 `experiments/` 아래. EXP-0 은 `exp0-20260801/FINDINGS.md`,
EXP-1 축별 판정은 `EXP1_FINDINGS.md`, 프로파일은 `prof-20260802/`.

## 7. 재검 — 계약 달성 뒤 추가로 찾은 것

관리자 요청으로 여유를 다시 뒤졌다. 둘을 찾았다.

```text
                    GET-only              1:9 혼합
게이트 (재검 전)  12.389 M / 25.05     10.116 M / G 20.41  S 21.68
A-1 flush 락 밖   12.529 M / 26.34     10.125 M / G 20.59  S  8.62
MEMSET            13.405 M / 25.99     10.777 M / G 19.87  S  8.97
                   +8.2%                +6.5%
```

### A-1 — flush 를 락 밖으로 (세 번째로 부호를 바꾼 손잡이)

캠페인 중간에 시도했다가 **졌던** 것이다(혼합 9.05 대 9.18). 그때는 refcount
감소와 워커 통계 뮤텍스가 그대로였고, 락 밖으로 빼면 `storage_flush_returns`
가 trylock 을 더 자주 이겨 완료 처리를 인라인으로 더 하느라 처리량을 팔았다.
**둘을 걷어낸 뒤에는 그 일이 싸서 지연 이득이 공짜로 온다.**

`reap` · `ext_setq_max` 에 이어 세 번째다. **옛 판정은 그것이 측정된 지형이
바뀌면 살아남지 못한다.**

### MEMSET — 한 줄

```c
memset(resp, 0, sizeof(*resp));              // mc_resp 1192 B
memset(resp, 0, offsetof(mc_resp, wbuf));    //          164 B
```

`mc_resp` 는 `char wbuf[1024]` 를 품고 `wbuf` 가 마지막 멤버다. GET 1 건마다
**1028 B 를 쓸데없이 쓰고 있었다** — 12 M ops/s 면 초당 12.3 GB 다. `wbuf` 는
쓰기 전에 채워지므로 0 으로 만들 이유가 없다.

대역폭만으로는 0.068 µs 를 예상했는데 실측은 그 두 배가 넘었다. 캐시 오염까지
걷힌 것으로 본다.

### 기각한 것

```text
A-2  reap × chain 재sweep      GET-only span 여유가 3.7 µs 뿐이라 여지가 좁다
A-3  평문 목적지를 응답 버퍼로  실제 비용이 0.012 µs (C_get 의 0.5%) 였다.
     내가 resp_allocate 와 같은 그룹으로 묶어 6.2% 로 잘못 읽었다 — 그 착오
     덕에 옆에 있던 진짜(1 KB memset)를 찾았다
```

## 8. B-1 — pipeline 축 (v2 config-matrix 의 v4 판)

off-box, v4 코드, span v3. 14 셀.

```text
pipe        32      64     128     256     384
GET-only  7.619   9.772  12.378  13.303  13.266  M
  span    25.06   25.94   26.79   26.03   25.98
혼합      6.590   8.217  10.194  10.770  10.109  M
  Gspan   21.47   22.24   20.65   19.85   21.44
  Sspan   10.53   10.53    9.59    8.94    8.93
```

**span 이 pipeline 깊이와 무관해졌다.** EXP-0 이 같은 축을 v4 이전 코드로 재서
얻은 GET span 은 `76.4 → 78.7 → 131.9 → 242.3` 이었다 — 제시량에 비례해 자랐다.
지금은 12 배 범위에서 4% 만 움직인다. **인라인 post 와 post 자리 수거가
없앤 큐가 여기 그대로 보인다.**

`pipe=256` 이 꼭짓점인 것은 그대로지만 **계약을 만족하는 점이 하나에서 셋으로
늘었다** — 128·256·384 가 모두 혼합 10 M 을 넘는다. MEMSET 이전 표(같은 축,
`7.245 / 9.474 / 11.926 / 12.354 / 11.816`, 혼합 `… 10.049 / 8.746`)에서는
256 하나뿐이었고 384 는 13% 퇴행했다. 지금 384 의 퇴행은 GET 0.3% 다.
**운영점이 한 pipeline 값에 얹혀 있지 않다는 뜻이다.**

## 9. B-2 — mcT 축 (v2 sensitivity 의 v4 판)

`pipeline=256` 고정, 나머지 운영값. 8 셀.

```text
mcT   GET-only   span                혼합      GET span   SET span   코어
 20   10.457 M   21.95 = 3.46+18.49   8.365 M   17.55      7.50      20.6
 24   11.651 M   24.48 = 3.53+20.94   9.504 M   18.36      7.96      24.5
 28   12.774 M   25.48 = 3.64+21.84  10.376 M   19.37      8.66      28.2
 30   13.303 M   26.03 = 3.65+22.39  10.770 M   19.85      8.94      29.9
```

### 천장은 호스트 SMT 가 정한다 — 예측으로 확인했다

호스트는 물리 16 코어 / SMT 32 스레드고 guest vCPU 30 개가 host CPU 0..29 에
1:1 로 핀돼 있다. 짝이 `(0,16)…(15,31)` 이므로 `taskset 0..N-1` 은 `N-16` 쌍을
공유한다. 이전 코어 측정(단독 0.410 M/s, 공유 쌍 합계 0.604 M/s)에서 공유
스레드는 단독의 `0.7366` 배다. 용량을 단독 스레드 환산으로 쓰면

```text
mcT   공유  단독   환산 용량
 20     8    12   5.89 + 12 = 17.89
 24    16     8  11.79 +  8 = 19.79
 28    24     4  17.68 +  4 = 21.68
 30    28     2  20.62 +  2 = 22.62
```

`mcT=20` 과 `30` 두 점으로 모형을 세우고 **나머지 두 점을 측정 전에
예측해 채널에 박아둔 뒤** 쟀다.

```text
        GET-only 예측 / 실측      혼합 예측 / 실측
 24      11.64 / 11.651  +0.1%     9.42 / 9.504  +0.9%
 28      12.75 / 12.774  +0.2%    10.32 / 10.376 +0.5%
```

**네 점 다 1% 안이다.** 코어 열이 전부 `mcT` 와 같으니 워커는 포화고,
곡선의 모양은 전적으로 SMT 공유 비율이 만든다.

이것이 말하는 바가 축 자체보다 중요하다. **소프트웨어 경합이 이제 측정
한계 아래라는 뜻이다** — 락이 남아 있었다면 스레드를 늘릴수록 모형보다
아래로 처졌을 것이다(§2 의 세 겹을 걷기 전이 그랬다). 그러므로 **30 vCPU
고정 하에서 남은 지렛대는 op 당 CPU 하나뿐이고, 1% 줄이면 1% 오른다.**

### 이 축은 프론티어다

span 이 처리량과 같이 움직인다(21.95 → 26.03). 계약을 만족하는 점은

```text
GET-only   20 · 24 · 28 · 30  전부
혼합       28 과 30 만  (24 는 9.504 로 처리량 미달)
```

`mcT=28` 은 30 보다 span 이 0.55 µs 짧고 처리량이 3.7% 낮다. 둘 다 계약
안이므로 운영값은 여유가 큰 30 을 유지하되, **span 여유가 더 필요해지면
28 이 준비된 대안**이다.

### 잡일 스레드는 축이 아니다

24 워커 구성에서 `/proc/<pid>/task/*/stat` 를 갈랐다.

```text
mc-worker × 24   200,119 tick
memcached (main)      21
mc-log · mc-assocmaint 0
```

**워커 외 전부 0.01%** 다. LRU maintainer·crawler·slab automove 는 스레드가
아예 없다.

## 11. bed 재현성 — 델타를 읽는 해상도

이 세션에서 **같은 구성**(기준 바이너리 `b4c18e97`, `mcT=30 W=40 nqp=4
pipe=256`)을 여러 번 쟀다. 서로 다른 실험의 대조군으로 찍힌 것들이라
독립 반복으로 쓸 수 있다.

```text
GET-only  n=11   평균 13.175 M   σ 0.133 (1.01%)   범위 13.017~13.405 (2.9%)
1:9 혼합  n= 9   평균 10.732 M   σ 0.112 (1.04%)   범위 10.536~10.830 (2.7%)
```

**2σ 가 약 2.0% 다. 이보다 작은 델타는 한 셀로 구별할 수 없다.**
§10 의 표적 셋(−0.26%, ±0.5%, ±0.5%)은 전부 그 안이므로 "무승부" 가 맞고,
`CPU_RELAX` 와 `-march` 가 `13.235 / 13.236` 으로 겹친 것도 이 분포 안의
같은 자리에 떨어진 것이다.

### 계약 판정을 분포로 다시 쓰면

```text
혼합 처리량  10.732 ± 0.112 M  (n=9)
계약선       10.0 M
초과폭       +7.3%  =  6.5σ
```

**단일 최고값(10.777)을 인용하는 것보다 이쪽이 강한 진술이다.** 최고값은
분포의 위쪽 끝이지 중심이 아니다. 계약은 운 좋은 한 창이 아니라 **9 개
독립 창의 중심이 게이트보다 6.5σ 위**라서 달성된 것이다.

같은 이유로 §최종 게이트의 `13.405 / 10.777` 은 **그 창의 값**이지 기대값이
아니다. 재현을 시도하면 `13.18 / 10.73` 근처가 나오는 것이 정상이다.

## 12. B-3 — 동시성 축 (v2 three-exp 의 v4 판)

v2 의 `qpxdepth` 는 `W ∈ {128, 256}` 이었다. **v4 에서 그 방향은 빈 축이다.**
Little 로 운영점 체류를 구하면

```text
GET-only  13.175 M × 26.03 µs / 30 = 워커당 11.54
1:9 혼합  10.732 M × 19.85 µs / 30 = 워커당  7.13
```

상한(창 40, ORD 64)이 필요치의 3.5~5.5 배다. **올려봐야 아무것도 안 바뀐다.**
그래서 질문을 뒤집어 **내려가면서** 쟀다 — 어디서 처음 물리는가.

### 창(W) 축

```text
 W    GET-only            혼합                    혼합 span
      처리량   span(adm)   처리량      z     n    GET     SET
40   13.175   26.03(3.65) 10.732      —     9   19.85   8.94
24   13.174   26.24(3.75) 10.850   1.35σ    2   19.64   8.75   ← 채택
16   13.328   27.19(7.36) 10.950   2.49σ    2   19.55   8.78
 8   11.809   80.08(64.5) 10.720      —     1   21.11  15.13   위반
```

**벽은 8 과 16 사이, 체류 11.54 가 있는 자리다.** Little 이 맞았다.

`W=8` 은 예측대로 **두 워크로드를 갈랐다** — GET-only(11.54 > 8)는 −11.4%,
혼합(7.13 < 8)은 −0.6%. 그런데 **span 예측은 반대로 틀렸다.** "체류가 줄면
대기도 준다"고 20.35 µs 를 예상했는데 80.08 이 나왔다.

```text
창은 backend 체류만 조인다        v2 15.54 로 실제로 줄었다
못 들어간 요청은 admit 에서 기다린다  adm 3.65 → 64.54
span v3 는 그 대기를 센다          그래서 총합이 3 배로 늘었다
```

코드로 확인했다: `extstore.c:807` 이 `outstanding < window` 로 post 를 막고
초과분은 대기 목록으로 가며, `t_start` 는 실제 post 시각(`:846`),
`t_enter` 는 span v3 진입(`storage.c:569`)이다. **큐를 앞으로 옮겨도 span
v3 는 따라온다** — §1 에서 걷어낸 대기 세 겹과 같은 성질인데, 나는 그걸
알면서 v2 식 직관으로 다시 계산했다.

### 왜 `W=16` 이 아니라 `W=24` 인가

`W=16` 이 혼합 +2.03%(2.49σ)로 더 크다. 그런데 `admit` 이 3.65 → 7.36 으로
두 배가 된다 — **여유 1.4 배는 큐가 서기 시작하는 자리**이고, 그 큐가
`W=8` 에서 `adm 64.54 / span 80.08` 로 터지는 걸 직접 봤다.

```text
W=16   오늘은 통과 (27.19 < 30, 여유 9.4%). 관측된 절벽의 어깨 위다
W=24   여유 2.1 배. admit 3.75 로 무변화 — 절벽에서 떨어져 있다
```

`W=24` 는 **기존 운영값을 엄격히 지배한다**: GET-only 무변화, 혼합은
처리량·GET span·SET span 셋 다 개선. **파는 것이 없다.** `+0.9%` 를 더
벌자고 어깨에 서지 않는다. `W=16` 은 "처리량 최대" 가 필요할 때의 대안.
