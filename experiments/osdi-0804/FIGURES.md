# 그림 명세 — exp1~4

각 실험이 **무엇을 그리고 그 그림이 무엇을 주장하는지**를 한 곳에 못박는다.
축·계열·출처 셀까지 정해 두는 이유는, 셀을 다 돌고 나서 "이걸로 뭘 그리지"를
정하면 축이 없는 데이터를 뒤늦게 발견하기 때문이다(오늘 밤 exp1 의 A/B 곡선이
그럴 뻔했다 — 스윕을 GET-only 에만 주려던 계획을 세 워크로드로 바꿨다).

```text
생성   tools/plot-osdi.py  (의존성 없음. SVG 직접 출력 — 기존 plot-*.py 와 같은 방식)
입력   experiments/night-20260806/rows.tsv   서버측(ariel 창)
       conversation.md 의 genie 보고         클라이언트 latency
출력   img/osdi-20260806/<figure-id>.svg
```

지표 규약: **처리량과 클라이언트 지연은 genie(memtier) 값**, span·성분·busy 는
ariel 창. 한 그림에 두 계기를 섞을 때는 범례에 출처를 적는다.

**제목 규약: 제목은 무엇을 그렸는지만 적는다.** 주장·결론·적합식은 제목에
넣지 않는다 — 그림 제목이 결론을 말하면 독자가 그림을 검증이 아니라 확인으로
읽는다. 주장은 주석 상자 마지막 줄과 이 문서의 "주장" 항목에 둔다.

```text
좋음   F2a  pipeline 축 — 클라이언트 지연과 span
나쁨   F2a — 같은 부하 축에서 두 지표가 반대로 간다      ← 제목이 결과를 논한다
좋음   F3   값 크기 대 CPU/op
나쁨   F3 — 값 크기: CPU/op 는 아핀이다 (2.00 µs + 4.05 ns/B)
```

**주석 규약: 그림마다 좌상단에 상자를 둔다.** 캡션은 붙어 다니지 않지만
그림은 혼자 돌아다닌다. 상자에 넣을 네 줄:

```text
① 달리한 것 — 이 그림에서 무엇만 바꿨고 나머지는 무엇으로 고정했나
② 점/막대가 무엇인가 — 셀 하나? 창 길이? 축 옆 숫자의 뜻은?
③ 계열 구분 — 색·실선/파선·채운점/빈점이 각각 무엇인가
④ 조건 — 빌드 sha, PROF 여부, 셀 지속 시간 (재현에 필요한 최소)
```

**축 규약: 로그 축을 쓰지 않는다** (관리자 지시 2026-08-06). 값 폭이 큰
그림에서 작은 막대가 안 보이는 것은 결함이 아니라 **그 자체가 주장**이므로
라벨로 값을 적는다(F1b 의 `0.00006 코어`가 그 예다).

## F1 — exp1: local vs remote, 워크로드별 지연-처리량 곡선

원형 DPA-Store Fig.15. **한 패널 = 한 워크로드**, 3 패널 가로 배치.

```text
패널      YCSB A (1:1) | YCSB B (1:19) | YCSB C (0:1)
x         처리량 (M ops/s)
y         클라이언트 지연 avg (ms, 선형)
계열      port(실선·원) / stock(파선·삼각)
점        pipeline 1·8·32·64·128·256·384 — 점 옆에 pipe 값을 작게
보조      각 계열의 정점에 세로 눈금, zipf θ=0.99 점을 속 빈 마커로 같은 패널에
출처      PT-* / ST-* (uniform), PTZ-*-Z256 / ST-*-Z256 (zipf)
```

**주장**: 원격화 대가는 워크로드에 따라 다르다 — 읽기 전용에서는 작고 쓰기
비중이 늘수록 커진다. skew 를 얹으면 그 순서가 유지된 채 전체가 왼쪽으로 민다.

> A 패널에는 **각주가 필수**다: 이 워크로드는 메모리 배치와 `item_lock` 경합이
> 겹쳐 있다(`stock-colocated/RESULTS.md §3-③`). 원격화 대가만 읽으면 안 된다.

## F1b — exp1: 메모리 노드 CPU ≈ 0  ✔ 그렸다

```text
막대 3 개 (선형 축 — 첫 막대는 보이지 않는다. 값은 라벨로 적는다)
  genie_memd        0.00006 코어   66.6 h 동안 15.3 s, prefill 포함, op 당 0.40 ns
  genie 박스 전체    27.9 코어      memtier 부하 생성기 (48 코어의 58.2%)
  guest memcached   29.9 코어      port 서버 (30 코어의 99.7%)
출처  genie 채널 2026-08-06 (`/proc/$(pgrep genie_memd)/stat` utime+stime 누적)
```

**주장**: one-sided READ 라 메모리 노드가 CPU 를 쓰지 않는다 — 서버보다
**50 만 배 적다.** XSTORE 가 "DrTM-Tree 는 24 코어를 다 쓰는데 XSTORE 는
절반 이하" 를 주장한 자리에 사실상 **0** 을 놓는다.

> 처음에 받은 "genie CPU 58.2%" 는 **박스 전체**라 memtier 가 대부분이었다.
> 두 수치는 다른 주장을 하므로 한 막대로 합치지 말 것 — 가운데 막대는
> "부하를 만드는 비용", 첫 막대가 "메모리 노드 비용" 이다.

## F2a — exp2: pipeline 곡선 (throughput–latency)

원형 XSTORE Fig.12a. **F1 의 C 패널과 축이 같지만 계열이 다르다** — 여기서는
port 한 계열에 **서버 span 을 두 번째 y 축**으로 겹친다.

```text
x         처리량 (M ops/s)
y1        클라이언트 지연 avg (ms)
y2        span v3 avg (µs) — 오른쪽 축
계열      GET-only / 1:9 혼합
표시      계약선 span=30 µs 를 y2 에 수평 파선
출처      BD2-GET-P* / BD2-MIX-P*  (60초 셀)
```

**주장**: 두 지표가 같은 부하 축에서 **반대로 움직인다.** 클라이언트 지연은
pipeline 에 비례해 오르는데 span 은 평평하다 — 계약이 재는 구간이 부하에
둔감하다는 것을 한 장으로 보인다.

## F2b — exp2: 지연 분해 스택 (이 캠페인의 대표 그림)

```text
x         pipeline (1·8·32·64·128·256·384, 로그 눈금)
y         서버 체류 µs (선형) — 누적 막대
층        que / pre / span v3 / post      (아래에서 위로)
패널      GET-only | 1:9 혼합
덧붙임    각 막대 위에 srv 총합, span 층만 색을 진하게(계약 구간)
출처      md/LATENCY_BREAKDOWN.md §8 표 = rows.tsv 의 BD2-b
```

**주장**: 서버 체류가 18 배 자라는 동안 계약 구간은 1.2 배다. 자라는 것은
`que` 와 `post` 이고 **둘 다 계약 밖**이다.

## F2c — exp2: v3 ↔ v4 같은 격자 비교

```text
좌 패널   span v3 대 pipeline — v3(원) vs v4(사각), 선형 y
우 패널   같은 x 에 srv 를 스택으로 두 개씩 (v3|v4 나란히)
출처      BD3(v3) / BD2-b(v4), KTC_0806_SPAN.md §6
```

**주장**: v4 는 span 을 11 배 줄였지만 `srv` 는 4% 줄였다 — **시간이 사라진
게 아니라 span 밖으로 옮겨갔다.** 좌 패널만 보면 11 배, 우 패널을 붙여야
정직하다. 두 패널을 반드시 같이 낸다.

## F3 — exp3: 값 크기

```text
x         값 크기 (16·32·64·152 B)
y1        CPU/op (µs) — 점 + 적합 직선 `2.00 + 0.00405·B`
y2        처리량 (M ops/s) — 보조
덧붙임    잔차를 아래 작은 패널에 (±2% 밴드)
계열      GET-only / 1:9 / SET-only
출처      V16 / V32 / V64 / V152
```

**주장**: 비용은 계단이 아니라 **아핀**이다. 고정비 2.00 µs 가 지배하고
바이트당 4.05 ns 다. 상한 152 B 에서도 바이트 항은 24% 에 그친다.

## F3b — exp3: 값 크기별 처리량–지연

```text
x         처리량 (M ops/s)
y         클라이언트 지연 avg (ms)
계열      GET-only / 1:9 혼합 / SET-only
점        값 크기 16·32·64·152 B — 점 옆에 크기를 적는다
출처      V{16,32,64,152}-W{1,2,3}, pipeline=256 고정
```

**주장**: 값을 키우면 운영점이 **왼쪽 위로**(느리고 적게) 민다. 세 워크로드가
같은 방향으로 밀리고, SET-only 가 제일 가파르다.

> ⚠️ 이 선은 **부하 곡선이 아니다.** 셀마다 pipeline 이 256 으로 같고 크기만
> 다르므로, 점을 크기 순으로 이은 **궤적**이다. F1·F2a 의 선(부하를 바꿔 그린
> 곡선)과 같은 것으로 읽으면 안 된다 — 그림 상자에도 그렇게 적었다.

> F3 의 두 번째 패널로 **성분 분해**를 넣는다: `xfer` 는 3.4 µs 늘고 `crypto` 는
> 0.25 µs 늘었다. **바이트 비용의 대부분이 전송이지 암복호가 아니라는 것**이
> 비밀 실행 환경 논문에서 물어볼 질문에 대한 답이다.

## F4a — exp4: 배칭 — 같은 노브, 반대 부호

```text
x         chain (1·2·4·8·12·16), reap=8 고정
y1        span v3 (µs) — 오르는 곡선
y2        srv (µs) 와 클라이언트 지연 — 내리는 곡선
표시      두 곡선이 교차하는 모양을 그대로 보이게 (이중 축)
출처      E4-C*R8  (c8 은 재시행값 13.037 을 쓴다 — 첫 셀은 낮았다)
```

**주장**: 서버 지표와 사용자 지표가 **같은 노브에 반대로 반응한다.**

## F4b — exp4: 두 노브의 역할 분리

```text
좌   admit 대 유효 배치 min(chain,reap) — chain 축(●)과 reap 축(○)이 겹친다
우   v2    대 같은 x                    — 두 축이 갈라진다
출처 E4-C{1,2,4,8}R8 과 E4-C8R{1,2,4,8}
```

**주장**: `admit` 은 두 노브에 **대칭**(트리거 B 때문), `v2` 는 `reap` 에만
반응한다. 왼쪽 그림에서 두 계열이 포개지고 오른쪽에서 벌어지는 것이 증거다.
**성분 분해가 없으면 이 그림은 못 그린다** — 처리량만으로는 두 축이 그냥
"비대칭"으로만 보인다.

## F4c — exp4: 계약 회랑

```text
x     chain, y 처리량. 혼합 10 M 수평선, GET-only 10 M 수평선
음영  혼합이 10 M 을 넘는 구간(chain ≥ 2)을 회랑으로 칠한다
```

**주장**: chain 노브가 존재하는 이유는 **혼합 조항**이다 — GET-only 는
chain=1 에서도 통과하고 혼합만 미달한다(9.653 M).
