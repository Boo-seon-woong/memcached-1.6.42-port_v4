# SET-only 10M ops/s — 요구조건 산정

작성 2026-07-29. 목표를 SET-only 10M ops/s로 둘 때 **op당 CPU 비용과 동시성이
어디까지 확보돼야 하는지**를 실측 기반으로 역산한다.

## 기준 실측 (2026-07-29, mc28/W24/nqp2/hp22)

```text
GET-only  10.12~10.25 M ops/s   프로세스 CPU 2.50 µs/op   guest busy 28.1/30
SET-only       0.32 M ops/s     프로세스 CPU 26.9 µs/op   memcached 이용률 31%
                                워커 점유 86.8 µs/op (CPU 31%, 대기 69%)
                                span 5.03 µs (crypto 1.05 + sync 1.90 + xfer 2.48)
```

## 1. CPU 예산 — 결론: **op당 2.57 µs**

10M을 내려면 예산은 GET이 10.12M을 낼 때 쓴 자원과 같다.

| 기준 | 예산 |
|---|---|
| guest-wide | 28.1 core-s ÷ 10M = **2.81 µs/op** |
| memcached 프로세스 | 25.7 core-s ÷ 10M = **2.57 µs/op** |

```text
현재 SET  26.9 µs/op  →  목표 2.57 µs/op  →  10.5배 절감 필요
참고 GET   2.50 µs/op  →  즉 SET을 GET과 동급 비용까지 내려야 한다
```

SET은 GET이 하지 않는 일(원격 슬롯 alloc/free, item alloc, 해시테이블
replace, 구 항목 정리)을 추가로 하므로, **GET과 동급**은 매우 공격적인
목표다. 이 숫자를 먼저 인지하고 시작해야 한다.

## 2. 동기 구조의 하드 상한 — 비동기화는 전제 조건

현재는 워커가 자기 WRITE CQE를 busy-wait하므로 워커당 동시성이 1이다.
따라서 처리량은 `워커 수 ÷ SET 1건의 벽시계 시간`으로 묶인다.

```text
CPU를 0으로 만들어도:  28 워커 ÷ 5.03 µs(span) = 5.57 M/s
```

**동기 구조로는 10M이 원리적으로 불가능하다.** CPU 최적화를 아무리 해도
span(암호화 시작→CQE)이 워커를 점유하는 한 5.6M이 천장이다. 비동기화는
선택지가 아니라 **전제**다.

구조와 착수 시 쟁점은 `md/GET_SET_CONCURRENCY.md` 참조.

## 3. 동시성 — 병목이 아니다

비동기화 후 필요한 wire 미완료 건수는 Little's law로 나온다.

```text
in-flight = 10M/s × 2.48 µs(xfer) = 25 건
가용      = W(24) × worker(28)    = 672 건      여유 27배
```

클라이언트 측도 이미 충분하다 — `t28 c4 p160` = 17,920 in-flight이고,
10M × 1.7 ms(클라이언트 왕복) = 17,000이 필요치다.

**즉 동시성은 확보돼 있고, 구조만 바꾸면 된다. 남는 문제는 전부 CPU다.**

## 4. CPU 예산 안에서 이미 확정된 비용

실측으로 고정된 두 항목만으로 예산을 넘는다.

| 항목 | 실측 | 성격 |
|---|---:|---|
| AES-GCM encrypt | 1.05 µs | 계산. 큰 절감 여지 적음 |
| SYNC_FOR_DEVICE ioctl | 1.90 µs | **SET당 1회 — 배치 없음** |
| 소계 | **2.95 µs** | 예산 2.57 µs를 이미 초과 |

### 여기서 나오는 가장 큰 단일 레버: SYNC 배치화

GET은 drain 한 번에 평균 **13건**의 READ를 모아 `SYNC_FOR_CPU` advise를
**1회**만 호출한다(실측 `objects_read / (drain_calls − drain_empty) = 12.97`).
그래서 GET의 sync 비용은 op당 0.34 µs로 상각된다.

SET은 `extstore_worker_post_write()`가 **쓰기 1건마다** `SYNC_FOR_DEVICE`를
호출한다(`extstore.c:764-772`). 상각이 전혀 없다.

```text
sync 1.90 µs → 6배 상각 시 0.32 µs
crypto + sync = 1.37 µs,  나머지 예산 1.20 µs
(참고: GET의 비-sync 작업은 약 2.2 µs)
```

## 5. 종합 — 10M SET의 성립 조건

| # | 조건 | 성격 | 현재 |
|---|---|---|---|
| 1 | **비동기 재개 구조** | 필수 전제 (없으면 5.6M 천장) | 미착수 |
| 2 | **SYNC_FOR_DEVICE 배치화** | 필수 (없으면 예산 초과) | 미착수 |
| 3 | CPU/op ≤ 2.57 µs | 목표 | 26.9 µs |
| 4 | wire 동시성 25건 | **충족** (672 가용) | 확보됨 |
| 5 | 클라이언트 in-flight 17K | **충족** (17,920) | 확보됨 |

조건 1·2를 모두 달성해도 남는 예산은 **1.20 µs**이고, 그 안에서 프로토콜
처리·item alloc·원격 슬롯 alloc/free·해시테이블 replace·응답 구성을 모두
끝내야 한다. GET이 동급 작업을 약 2.2 µs에 하고 있으므로, **SET은 crypto를
제외한 모든 부분에서 GET보다 싸야 한다**는 뜻이다.

**판정: 10M SET은 실현 가능성의 경계선에 있다.** 불가능하다고 단정할 근거는
없지만, 구조 변경 2건 + GET을 능가하는 효율이 동시에 필요하다.

## 6. 착수 순서 (권고)

```text
1) SET 26.9 µs/op의 내역 규명   ← 지금 미상. 프레임 포인터 빌드로 프로파일
   (프로파일 상위에 slabs_alloc/slabs_free가 보이나 스택이 끊겨 미확정)
2) SYNC_FOR_DEVICE 배치화        ← 단독으로도 효과, 구조 변경 없이 가능
3) 비동기 재개 구조 전환         ← 가장 큰 작업. 1)의 결과가 상한을 정한다
```

1번을 건너뛰면 26.9 µs 중 무엇이 줄어드는지 모르는 채 설계하게 된다. 2번은
1번과 독립적으로 착수 가능하고 예산 산정을 바꾸므로 먼저 해볼 가치가 있다.

> 이 문서의 모든 수치는 GET-only 10.12M을 낸 것과 동일한 자원(28 vCPU 서버,
> 30 vCPU guest)을 전제로 한다. 하드웨어가 바뀌면 예산도 비례해서 바뀐다.

| # | 조건 | §5 판정 당시 | 현재 |
|---|---|---|---|
| 1 | 비동기 재개 구조 | 미착수 | 세 형태 구현. 둘 탈락(watermark 2배 손실 미규명 / 연결 파킹 기각), **셋째 `pac`이 1차 통과** — co-located A/B +21%, 클라이언트 p99 −18%, 결함 0. off-box 재판정 대기 |

| 3 | CPU/op ≤ 2.57 µs | 26.9 µs | 동기 7.29 µs → **pac+배치 5.77 µs**(co-located 서버 CPU만). 28코어 환산 4.85M, off-box 보정 후 ≈4.5M |
| 4 | wire 동시성 25건 | 충족 | 충족 — 단, **연결 파킹 설계에서는 무효**: 실질 동시성이 window가 아니라 연결 수로 제한된다는 것이 실측 교훈. pac은 연결을 묶지 않으므로 이 함정을 피한다 |
| 5 | 클라이언트 in-flight | 충족 | 충족 |

§6 착수 순서의 1)(내역 규명)은 `SET_COST_ATTRIBUTION.md`로 완료. 구조
후속인 publish-at-command는 구현·1차 실측을 통과했다(`SET_WORKFLOW.md`
§0-2). off-CPU 간극 규명은 **pac 적용 후 상태에서** 하는 것으로 순서를
바꿨다 — 간극의 일부를 pac이 이미 제거했기 때문이다(§3 갱신 주석).

**2026-07-30 동기 재측정** (memtier@genie, 서버 `cca9807`+`no_ext_async_set`
— 초판의 "main 7a09928" 귀속은 오기): SET-only **2.27M @ span 6.21µs**,
워커 점유 12.3µs/op. 이 span 기준 동기 상한은 28÷6.21µs = **4.51M** — 즉 5M은
동기 구조로는 span보다 점유를 더 줄여야 하는 모순이라 불가하고, 비동기 전환
후 CPU ≤ 5.6µs/op(28÷5M)이 5M의 조건이다. pac이 동기 대비 CPU/op를 −20%로
낮췄으므로 이 조건은 처음으로 사정권에 들어왔다 — 다만 확인은 co-located가
아니라 off-box 정본 bed에서 해야 한다. 상세는 `SET_WORKFLOW.md` §0-1·§0-2.

### 7-1. 1차 목표 (2026-07-30 설정): SET-only 5 M ops/s, span < 30 µs

10M 이전의 중간 관문. 현재 위치와 남은 거리:

```text
필요 CPU/op    28 ÷ 5M = 5.60 µs
현재           5.77 µs   (co-located 서버 CPU만, pac + SYNC 배치)
off-box 보정   co-located 환산이 ~7% 낙관적(GET 11.11 환산 vs 10.35 실측)
               → 실질 ≈ 4.5 M, 5M까지 CPU/op 약 10% 절감 필요
span           post→CQE 6.36 µs — GET과 같은 정의로는 이미 30 µs 아래
```

**span 조건은 정의를 맞추면 이미 충족이다.** GET 게이트가 재는 구간(post →
CQE)에서 SET는 6.36 µs다. seal부터 재는 현재 SET 정의의 240 µs는 수락 큐잉을
포함한 다른 양이고, 포화 상태에서 그 값이 커지는 것은 Little의 법칙이지 결함이
아니다(`SET_WORKFLOW.md` §0-3).

**남은 것은 처리량 10 %뿐이고, 대상은 SET 고유 비용 2.29 µs**(같은 bed에서
SET 5.77 − GET 2.52). 프로파일이 다음 단계다.
