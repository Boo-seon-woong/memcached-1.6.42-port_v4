기준이라 계약에 대해 아무것도 말해주지 않는다.

빌드 `c8aeae5bc1804fe025814dc2` (`v3-set-pac` + 성분 분해). **코드 변경 전**이다.

## 1. pipeline 으로는 계약을 못 지킨다 — 교차점이 없다

```text
pipe      8      16      32      64     128     256
ops    3.451   5.418   7.644   9.669  11.676  11.932
Gv3    34.02   48.48   76.36   78.70  131.91  242.29
```

**가장 낮은 pipe=8 에서도 34.02 µs 로 이미 위반이고 처리량은 3.451 M 이다.**
30 µs 를 만족하는 지점 자체가 없다. 처리량은 pipe 에 거의 비례해 오르고 span
은 그보다 빠르게 오르므로 두 곡선은 만나지 않는다.

이것이 EXP-0 사양에 적은 두 결말 중 후자다 — **구조를 바꿔야 한다.**

## 2. 그런데 데이터 경로는 이미 계약 안이다

세로로 보면 다른 그림이 나온다. `v2` 열(= 실제 RDMA 왕복 + 복호)은:

```text
GET-only   17.44 → 25.16      혼합 GET   15.94 → 26.59
혼합 SET   16.34 → 15.13      SET-only    7.69 →  7.84
```

**전부 30 µs 아래이고, pipeline 을 32배 늘려도 거의 안 움직인다.**
계약을 막는 것은 원격 접근 자체가 아니라 그 앞뒤에 붙은 대기다.

```text
Gv3 242.29 =  admit 217.12  +  v2 25.16      admit 이 90%
Sv3 2380.29 = admit 0.61 + v2 7.84 + ret 2371.84    ret 이 99.7%
```

**admit 을 없애면 GET-only 는 pipe=256 에서 11.93 M @ 25.16 µs, 혼합은
10.06 M @ GET 26.59 / SET 15.13 µs 다. 둘 다 계약을 통과한다.**

## 3. admit 은 큐가 아니다 — 상류의 submit 배칭이다

`memcached.c` 가 io_queue 를 **연결 20개**가 쌓일 때까지 붙들고 있다:

```c
if (t->conns_tosubmit++ > 20) { thread_io_queue_submit(c->thread); }
```

pipe=8 의 backend 체류는 `34.02 µs × 3.451 M = 117 건`, 워커당 3.9 건이다.
`W=40` 이니 **파킹이 일어날 수 없는데도** admit 이 16.57 µs 다. 큐가 아니다.

pipeline 이 깊을수록 연결 하나의 파싱이 길어져 같은 20개를 모으는 데 더
걸린다. 그래서 부하와 함께 자란다(16.57 → 217.12).

> **도어벨 상각은 여기서 안 나온다.** `ext_batch=32` 라 한 번의 `ibv_post_send`
> 가 최대 32개다. 체인 1280개(20 연결분)는 40번, 체인 64개(1 연결분)는 2번 —
> **요청당 도어벨 수가 같다.** 연결을 모아서 얻는 것은 지연뿐이다.

높은 pipe 에서는 두 번째 조각이 붙는다. pipe=256 의 체류는 워커당 96 건이라
`W=40` 을 넘어 56 건이 wait list 에 눕는다. 그 파킹은 `storage_get_item`
뒤라 span 안이다. **admit = submit 배칭 + 창 파킹**이고, 저부하에서는 앞의
것만, 고부하에서는 둘 다다.

## 4. ret 은 이벤트 루프 한 pass 다

`storage_flush_pending_writes` 는 4단계에서 앞선 배치의 CQE 를 최대 256개
거둔다. 그것이 CQ 를 비우면 호출부(`worker_libevent`)가 `outstanding == 0` 을
보고 **블록 전체를 건너뛴다** — 그 안에 있던 `storage_flush_returns()` 까지.
완료는 ready 목록에 놓인 채 arm 된 drain 이벤트를 기다리고, 그건 다음 pass 다.

flush 자신은 재개할 수 없다. 큐 상한 경로가 `do_store_item` 의 `item_lock(hv)`
아래에서 flush 를 부르는데 `return_cb` 는 같은 버킷의 `item_lock` 을 다시
잡는다. **루프 레벨 호출부는 락이 없다** — 거기서 비우면 된다.

부하와 함께 자라는 것이 이 진단과 맞는다:

```text
SET-only ret    pipe 16   99.21      64  443.13     256  2371.84
혼합 SET  ret   pipe 16   16.95      64   47.26     256   173.11
```

SET-only 가 훨씬 나쁜 것도 설명된다 — GET 이 없으면 워커의 `outstanding` 이
WRITE 뿐이라 4단계 drain 이 매번 CQ 를 완전히 비우고, 건너뛰기가 항상 일어난다.

## 5. Little's Law 재확인

```text
pipe=256 GET-only   242.29 µs × 11.932 M = 2,891 건 체류
목표                  30 µs × 10 M       =   300 건
```

24배 초과다. 그런데 **무대기 서비스 시간이 25.16 µs** 이므로 300 건이면
`300 / 25.16 µs = 11.9 M/s` 다. 지금 나오는 처리량과 같다.
**용량은 이미 있다. 대기만 걷어내면 된다.**

## 6. 부수 관측

- **busy 가 pipe 8~32 에서 23.6~24.3 에 머문다.** 30 코어 중 6개가 논다.
  이 구간의 처리량 한계는 CPU 가 아니라 동시성이다. 64 부터 28.6 → 29.9 로
  붙으면서 CPU 가 이어받는다.
- **혼합의 GET admit 이 GET-only 보다 크다**(pipe 8 에서 21.47 대 16.57).
  SET 이 섞이면 pass 가 길어진다.
- **SET 의 admit 은 전 구간 0.5~0.7 µs** 다. pac 이 즉시 큐에 넣기 때문이고,
  설계 의도대로 동작한다.
